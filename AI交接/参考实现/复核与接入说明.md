# 当前时点滑块：复核结论、实现与接入说明

2026-10-07。依据上传的菜单材料及前一份滑块报审材料。附件中的部署指令视为项目说明，本次没有执行你的本地构建或发卡操作。

结论：滑块可以做。现在应先修日期进入提交链的接口，再接滑块；菜单正则的作用范围已经正确。下面交付的是独立验证过的参考实现及明确修补点，尚不是完整角色卡的已集成版本。

## 1. 本份原文能确认什么

| 项目 | 结论与影响 |
| :--- | :--- |
| `chips` 定义 | 第一节全文里确实有 `const chips = (...) => ...`，是箭头函数。按钮只提供 `data-xds-fill` / `data-xds-value`，需要控制器执行填值。 |
| 填值方式 | `xdsMenuSetValue` 用输入框所属文档的原生 setter，并派发同一文档的 `input` 事件。这适合继续复用，不能换成只赋 `.value`。 |
| 提交字段清单 | 文档第 1860–1875 行的 `xdsMenuIntro` 中，`names` 只有六项，没有 `custom_timepoint`。如果后续仍按上一份材料所说读取 `values.custom_timepoint`，就会一直取默认值。上一份“已经加入日期”的描述与本份摘录不一致，须核对实际打进卡内的版本。 |
| 菜单正则 | `markdownOnly: true`、`promptOnly: false`、`placement: [2]` 是 AI 消息的显示层替换。无需把菜单生成条改成提示词正则。 |
| 绑定和卸载 | 本份没有实际 `data-xds-fill` 事件处理、`submit-custom` 处理、初始化和清理函数的完整代码，无法认定现有控制器已正确处理重复绑定、跨会话提交或重渲染。 |

特别澄清“八个日期污染”这句话：**显示层 `replaceString` 有八个日期，不等于聊天原始消息中有八个日期**。ST 1.14.0 的正则引擎对 `isMarkdown` 和 `isPrompt` 分别检查作用范围；这份配置不会在生成路径把 `<IdentityMenu />` 展开成菜单。若原始消息本身写入了 HTML，或时间解析器读取渲染后的 DOM，才可能读到菜单日期。材料没有附 `parseXianmengFromText` 函数及其调用点，不能把“必然取到第一个 1577 年日期”当作已证实的运行结果。

不管现有错误走哪条路径，正确接口都是：**开局时间只从已提交的 `custom_timepoint` 值读取，不能扫描整份菜单或整条开局消息中的第一个日期**。来历字段也可能包含早年的日期。

- [ST 1.14.0 消息 HTML 清洗](https://github.com/SillyTavern/SillyTavern/blob/1.14.0/public/script.js#L1763)。
- [ST 1.14.0 消息 class 改名前缀](https://github.com/SillyTavern/SillyTavern/blob/1.14.0/public/scripts/chats.js#L1915)。本实现用 `data-*` 选择器，避免依赖被改名的 class。

## 2. 固定的交互与时间规则

1. 八个预设值逐字保持原按钮字符串，默认第 2 点：1578 年三月初三。
2. 打开菜单、初始化、回显及重新绑定，只读输入框，不填默认值，不写历基准、日历、段位或锚点。
3. 拖动滑块把选中的预设字符串写进同一菜单的文本框，触发既有 `input` 链。文本框仍是提交权威；滑块没有 `name="custom_timepoint"`。
4. 手填日期与预设日期相同时，滑块显示相应点，但不重写原文字。其他合法日期保留原值，滑块显示最近且不晚于该日期的参考点。早于首点/晚于末点也保留日期，并提示超出预设范围。
5. 如 `仙盟历 1579 年 · 六月初七`，打开或回显后还是初七。要主动改成六月初一，可以拖动滑块，也可点“采用参考点”；不能靠初始化吸附。
6. 空值提交采用初三；非空而无法识别的值应报错并阻止本次开局提交，不能默默变成初一。完成校验后再执行身份切换、发送或写状态。
7. 滑块只是选择开局日期。不能由索引推导“某剧情已经发生”、补锚点或提升段位。晚期开局如需预置历史事实，要单独定义初始化规则。
8. 仅滑块增强失败且原控制器仍工作时，旧按钮可继续填值。整个卡内脚本不运行时，填值、切身份、落款发送都依赖的 JS 已失效；原生输入框可编辑不代表整条开局链可用。

这里有一个必须突破的原报审范围：“只动菜单和面板、不动状态机”不能成立。现有控制器就在状态机中，而且提交字段、默认值和解析输入属于状态机接口；这些不修，滑块看起来可用也不能正确开局。事件应随现有首楼控制器启动，不应等 HUD 挂载。

## 4. 原项目接入方法

### A. 菜单生成器

将 `timepoint-slider.cjs` 放在 `src/first_floor_rebuild/` 下，合并 `menu-builder.patch`，或核对后采用随附的 `menu-builder.cjs`。

三处改动是：引入模块；把 `TIMEPOINT_CSS` 附加到原 `MENU_CSS`；把原“当前时点”整段换成 `${renderTimepoint(instanceId)}`。其他字段及旧按钮协议保留。

增强区初始带 `hidden`，旧按钮初始显示。范围输入原生支持方向键；触控高度 44px，移动触控设备设 `touch-action: pan-y`。只有成功初始化的那一组日期按钮会被隐藏。

### B. 运行时放在首楼状态机控制器

把 `timepoint-slider.cjs` 的内容通过现有构建链拼接进**真正的状态机源**，与 `xdsMenuHost` / `xdsMenuSetValue` 同一脚本可见。也可以先复制其中 `function xdsTimepointModule() { ... }` 函数定义用于人工接入。

运行时函数与构建时模块必须来自同一文件；不要另手抄一份日期数组。不要往消息 HTML 放 `<script>`，也不要把初始化移进 HUD 的 `mount()`。

在现有首楼控制器启动路径中加入：

```js
const xdsTimepoint = xdsTimepointModule();
let xdsTimepointHandle = null;

try {
  xdsTimepointHandle = xdsTimepoint.install({
    host: xdsMenuHost(),
    ownerWindow: window, // 当前酒馆助手脚本 iframe
    setValue: xdsMenuSetValue,
  });
} catch (error) {
  console.warn('[XDS timepoint] 初始化失败，保留原日期入口', error);
}
```

在现有控制器销毁/换卡清理函数中加入：

```js
if (xdsTimepointHandle) {
  xdsTimepointHandle.dispose();
  xdsTimepointHandle = null;
}
```

这两个片段必须放在彼此共享变量的现有作用域里；上面的 `xdsTimepoint` 还用于 C 节提交校验。材料没有给出原启动与清理函数，故这里按用途指明接入点，不能冒充已完成原控制器的精确行号补丁。

安装器在宿主 document 只维持一组自己的委托监听，覆盖 `input`、`change` 和“采用参考点”点击。同一宿主重新安装会先清掉上一组；iframe `pagehide` / `unload` 时也清理。仍应接入现有销毁函数，不把浏览器卸载事件当作所有酒馆助手生命周期的保证。

`MutationObserver` 只处理新增/移除的元素结构，初始化重渲染菜单；不会观察属性，也不会因自己的输出文字变化反复扫描。事件按最近的日期区块和菜单作用域寻找输入框，不用全局 ID，也不用 iframe 中的 `instanceof HTMLElement` 判断父文档节点。

宿主传入复用现有 `xdsMenuHost()`。其已给出的实现会一路向上找可访问父窗口；若你的酒馆还嵌在其他同源页面中，应确认它返回的 document 实际包含聊天区，而不是外层站点。新组件不凭固定 `window.parent` 层数猜宿主。

### C. 修正 `xdsMenuIntro` 的取值与序列化

将本份摘录里的两个数组替换为：

```js
const names = [
  'custom_name', 'custom_gender', 'custom_age', 'custom_cultivation',
  'custom_sect', 'custom_timepoint', 'custom_origin',
];
const limits = [64, 16, 32, 96, 128, 64, 1800];
```

保留现有逐字段取值循环，在循环之后、返回开局文字之前加入：

```js
const startTime = xdsTimepoint.resolveTimepoint(values.custom_timepoint);
```

在原返回文本中插入或替换日期行，保证**恰好一行**：

```js
'• 当前时点：' + startTime.value + '\n' +
```

`resolveTimepoint('')` 返回初三默认值；非空无效值抛错。`startTime.value` 保留所提交日期的文字（只去首尾空白），不会把六月初七改成六月初一。

提交处理必须先读取表单、调用 `xdsMenuIntro` 完成全部校验，再切身份/发送/写基准。异步切换会话或重渲染前，先捕获本次的开局文本与 `startTime`；后续步骤使用这个快照，避免读已被替换的表单。现有 `xdsMenuChatKey()` 可用于在每个异步步骤后确认仍是同一会话；检测到切换就中止本次提交，不在新的会话中继续写入。

不能为了用到这里的模块，把原本可独立运行的旧按钮处理改成依赖滑块安装成功。模块的数据/校验函数与 `install()` 分离：即使安装失败，提交端仍能校验日期。

### D. 修正开局时间解析入口

首选方案是让现有开局初始化函数直接接收已捕获的 `startTime` 或 `startTime.value`。不要在拖动事件里写历基准。

若现有状态机只能从已发送的自设开局消息恢复时间，在它现有的**自设开局分支**使用：

```js
const startTime = xdsTimepoint.resolveFromIntro(submittedOpeningText);
// startTime.ym 例如 1579.06，startTime.day 例如 7。
// 将这两个值接到现有“自设开局基准”的赋值处。
// 保留现有写入 API、会话检查、快照与回滚协议。
```

`submittedOpeningText` 在这里表示该分支已拿到的开局消息正文，不是一个现有变量名。该函数仅寻找唯一的 `• 当前时点：` 行；来历中其他日期不会抢占。缺少该行或出现重复行会报错。**不要对普通后续叙事通用调用这个函数，也不要再从全部消息中抓第一个日期。**

有开局事件识别但只有“整条文本抓日期”的入口时，只换其输入来源与空值规则；不要借本次滑块工作重写推进、闸门或历史回滚。

旧存档已有历基准时直接沿用，不能因为重新显示菜单就再次初始化。旧版开局消息可能没有日期行；这种情况应在明确的旧版迁移分支处理：缺少基准时采用统一初三默认值并只初始化一次，不把它混同于“新提交的非空日期解析失败”。`resolveFromIntro` 的严格接口适用于新版已序列化开局文本，不应直接拿它重扫全部旧聊天。

模块的日期解析支持本文八个预设、中文日数（初/廿/卅）和数字日期，只做基础格式及范围校验（月份 1–12，日数 1–31）。没有套用公历、闰月或某月天数。在赋给历基准前，仍须与原项目仙盟历的月长规则一致；若现有时钟规定每月 30 日，应在这个单一解析器中收紧日数上限，不能让显示和时钟各自接受不同的日期。原时钟实现没有附在本份材料中。

### E. 菜单正则

维持原 `identityMenuScript` 配置。不要把菜单 HTML 的生成条改成 `promptOnly: true`，那会在生成路径展开整份菜单。

是否另有 `<IdentityMenu />` 标记清理条，应查已有 `hideIdentityPickScript` 等完整配置，不为本次滑块盲目追加重复正则。验收时直接查看生成预览及世界书扫描输入，确认没有整份菜单及七个未选中的日期。

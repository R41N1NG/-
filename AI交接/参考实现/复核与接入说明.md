## 2. 固定的交互与时间规则

1. 八个预设值逐字保持原按钮字符串，默认第 2 点：1578 年三月初三。
2. 打开菜单、初始化、回显及重新绑定，只读输入框，不填默认值，不写历基准、日历、段位或锚点。
3. 拖动滑块把选中的预设字符串写进同一菜单的文本框，触发既有 `input` 链。文本框仍是提交权威；滑块没有 `name="custom_timepoint"`。
4. 手填日期与预设日期相同时，滑块显示相应点，但不重写原文字。其他合法日期保留原值，滑块显示最近且不晚于该日期的参考点。早于首点/晚于末点也保留日期，并提示超出预设范围。
5. 如 `仙盟历 1579 年 · 六月初七`，打开或回显后还是初七。要主动改成六月初一，可以拖动滑块，也可点“采用参考点”；不能靠初始化吸附。
6. 空值提交采用初三；非空而无法识别的值应报错并阻止本次开局提交，不能默默变成初一。完成校验后再执行身份切换、发送或写状态。
7. 滑块只是选择开局日期。不能由索引推导“某剧情已经发生”、补锚点或提升段位。晚期开局如需预置历史事实，要单独定义初始化规则。
8. 仅滑块增强失败且原控制器仍工作时，旧按钮可继续填值。整个卡内脚本不运行时，填值、切身份、落款发送都依赖的 JS 已失效；原生输入框可编辑不代表整条开局链可用。

这里有一个必须突破的原报审范围：“只动菜单和面板、不动状态机”不能成立。现有控制器就在状态机中，而且提交字段、默认值和解析输入属于状态机接口；这些不修，滑块看起来可用也不能正确开局。事件应随现有首楼控制器启动，不应等 HUD 挂载。

## 4. 原项目接入方法

### A. 菜单生成器

将 `timepoint-slider.cjs` 放在 `src/first_floor_rebuild/` 下，合并 `menu-builder.patch`，或核对后采用随附的 `menu-builder.cjs`。

三处改动是：引入模块；把 `TIMEPOINT_CSS` 附加到原 `MENU_CSS`；把原“当前时点”整段换成 `${renderTimepoint(instanceId)}`。其他字段及旧按钮协议保留。

增强区初始带 `hidden`，旧按钮初始显示。范围输入原生支持方向键；触控高度 44px，移动触控设备设 `touch-action: pan-y`。只有成功初始化的那一组日期按钮会被隐藏。

### B. 运行时放在首楼状态机控制器

P0 完整快照中的首楼闭环在本地 `卡片脚本/状态机.js`。P1 可以先在这个工作文件实施；最终以构建输入及卡内内容比对确认生效。把共享文件中的 `function xdsTimepointModule() { ... }` 放到这个脚本中可见的位置；最好由现有构建链从共享文件注入，不另维护一份日期表。

运行时函数与构建时模块必须来自同一文件；不要另手抄一份日期数组。不要往消息 HTML 放 `<script>`，也不要把初始化移进 HUD 的 `mount()`。

在状态机控制器作用域建立共享模块：

```js
const xdsTimepoint = xdsTimepointModule();
```

现有 `runtime.attach(surface)` 会附着聊天 document 和同源消息 iframe。推荐在它的 `runtime.scan(surface)`（本快照第 3402 行）之后加入：

```js
try {
  const timepointHandle = xdsTimepoint.install({
    host: surface.defaultView, // 本次实际附着的 document 所属窗口
    ownerWindow: window, // 当前酒馆助手状态机 iframe
    setValue: xdsMenuSetValue,
  });
  runtime.cleanups.push(() => timepointHandle.dispose());
} catch (error) {
  console.warn('[XDS timepoint] 初始化失败，保留原日期入口', error);
}
```

这样清理由原 `runtime.dispose()` 执行，无需新建第二套控制器生命周期。原 `runtime.docs` 限制每个 document 只 attach 一次；安装器的宿主单例再保证重装不保留旧监听。上述接线片段针对本次完整快照，尚待生产项目与真实酒馆验证。

安装器在宿主 document 只维持一组自己的委托监听，覆盖 `input`、`change` 和“采用参考点”点击。同一宿主重新安装会先清掉上一组；iframe `pagehide` / `unload` 时也清理。仍应接入现有销毁函数，不把浏览器卸载事件当作所有酒馆助手生命周期的保证。

`MutationObserver` 只处理新增/移除的元素结构，初始化重渲染菜单；不会观察属性，也不会因自己的输出文字变化反复扫描。事件按最近的日期区块和菜单作用域寻找输入框，不用全局 ID，也不用 iframe 中的 `instanceof HTMLElement` 判断父文档节点。

首个宿主 document 仍由现有 `xdsMenuHost()` 找到；组件跟随原运行时实际 attach 的各个 document，避免只在最上层监听而漏掉消息 iframe。若酒馆嵌在其他同源站点中，仍须确认原 host 查找返回聊天宿主。

const names = [

保留现有逐字段取值循环，在循环之后、返回开局文字之前加入：

```js
const startTime = xdsTimepoint.resolveTimepoint(values.custom_timepoint);
```

在原返回文本中插入或替换日期行，保证**恰好一行**：

```js
'• 当前时点：' + startTime.value + '\n' +
```

`resolveTimepoint('')` 返回初三默认值；非空无效值抛错。`startTime.value` 保留所提交日期的文字（只去首尾空白），不会把六月初七改成六月初一。

提交处理必须先读取表单、调用 `xdsMenuIntro` 完成全部校验，再切身份/发送/写基准。异步切换会话或重渲染前，先捕获本次的开局文本与 `startTime`；后续步骤使用这个快照，避免读已被替换的表单。现有 `xdsMenuChatKey()` 可用于在每个异步步骤后确认仍是同一会话；检测到切换就中止本次提交，不在新的会话中继续写入。

不能为了用到这里的模块，把原本可独立运行的旧按钮处理改成依赖滑块安装成功。模块的数据/校验函数与 `install()` 分离：即使安装失败，提交端仍能校验日期。

### D. 修正开局时间解析入口

首选方案是让现有开局初始化函数直接接收已捕获的 `startTime` 或 `startTime.value`。不要在拖动事件里写历基准。

若现有状态机只能从已发送的自设开局消息恢复时间，在它现有的**自设开局分支**使用：

```js
const startTime = xdsTimepoint.resolveFromIntro(submittedOpeningText);
// startTime.ym 例如 1579.06，startTime.day 例如 7。
// 将这两个值接到现有“自设开局基准”的赋值处。
// 保留现有写入 API、会话检查、快照与回滚协议。
```

`submittedOpeningText` 在这里表示该分支已拿到的开局消息正文，不是一个现有变量名。该函数仅寻找唯一的 `• 当前时点：` 行；来历中其他日期不会抢占。缺少该行或出现重复行会报错。**不要对普通后续叙事通用调用这个函数，也不要再从全部消息中抓第一个日期。**

新增快照第 2247 行优先读当前 AI 正文，随后读固定第 1 楼；两者都不能代替本次已接受开局的字段值。P1 须让第一次生成前的变量已包含选定日期；只等 AI 回复渲染后设置基准，会让第一轮世界书仍按旧日期扫描。具体接受消息、等待初始化的时序需要按真实宿主验证，不能靠固定延时猜测。

还需修两个直接使选定日期失效的分支：第 2093–2097 行缺状态栏时按 `SEG_TIME[段位]` 覆写日期；第 2263–2264 行换段清空 `时点加速` 后用它计算日历。前者应保留现有时间，后者应将“全程累计历时”与“本段推进计数”分开；现有第 2182–2186 行也使用 `时点加速` 推段位，不能只删清零而无视这个共同用途。详细处理要求见本批复核。

旧存档已有历基准时直接沿用，不能因为重新显示菜单就再次初始化。旧版开局消息可能没有日期行；这种情况应在明确的旧版迁移分支处理：缺少基准时采用统一初三默认值并只初始化一次，不把它混同于“新提交的非空日期解析失败”。`resolveFromIntro` 的严格接口适用于新版已序列化开局文本，不应直接拿它重扫全部旧聊天。

模块的日期解析支持本文八个预设、中文日数（初/廿/卅）和数字日期。新增完整生产快照已确认按每月 30 日计算，因此本次将共享解析器日数上限统一为 30：31 日拒绝提交，不截成 30 日。没有套用公历或闰月；显示、校验和基准必须一致。

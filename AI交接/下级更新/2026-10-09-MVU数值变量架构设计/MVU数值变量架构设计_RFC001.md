## 〇、提案背景与核心动因

在当前的跑书交互中，所有剧情与名器阶段均采用**纯布尔标记（Boolean Flags，只有 true/false）**控制。  
布尔值能有效管理“是否发生”，但无法表达“程度与渐进过程”：
1. **提问晋升的回答黑盒化**：当玩家询问 *“叶红缨，你如何才能晋升到第二阶？”* 时，模型因无法获知历史交合频次，只能空泛回复“需多次交合并内射”，缺乏具体进度感知；
2. **阶段跃迁缺乏量化台阶**：从一阶（初生）到二阶（情动），缺乏“内射浸润累计”的客观台阶，导致部分模型单次交互就直接越级，或多次交合后仍不晋升；
3. **心智与破境缺乏刻度**：女修由隐忍抵拒到生理迎合、再到心理依附，缺乏平滑过渡阶梯；神诅断路破境缺乏可视化的初元/成形器皿计数器。

本提案旨在设计一套**“轻量、零幻觉、防刷爆、无缝兼容现有 246 条世界书”**的 MVU 数值系统。

## 一、架构设计铁律（规避五大历史陷阱）

针对 LLM 与酒馆状态机的特性，确立四大底层设计铁律：

1. **铁律 A：动作申报制，严禁 AI 做心算（规避幻觉陷阱）**  
   - 严禁让模型在状态栏输出当前总分（如 `<浸润度>40/100</浸润度>`）；
   - **模型仅负责输出“客观动作事实”**（如 `<名器互动>灼酒流炎穴: 深度交合内射</名器互动>` 或 `<名器微变>灼酒流炎穴+1</名器微变>`）；
   - **由卡内 JavaScript 状态机执行严格单向累加**（`+1`）与边界截断（Clamp 0~5）。
2. **铁律 B：消息层快照回溯（规避 Swipe/重抽数值滚雪球）**  
   - 数值变量必须与消息层（`{type: 'message', message_id: N}`）严格同步；
   - 第 N 楼的数值运算基准必须基于第 N-1 楼快照；重抽（Swipe）或编辑当楼时，状态机重新基于 N-1 楼计算，杜绝重复累加。
3. **铁律 C：上游蓄水池原则（零破坏现有世界书）**  
   - 数值系统作为现有布尔系统的上游驱动引擎；
   - 当浸润数值达标（如 `progress >= 5`）时，状态机自动派生点亮既有的 `known['灼酒流炎穴二阶段'] = true`；
   - **现有的 246 条世界书、EJS 闸门与剧情推进系统 100% 保持原样，无需任何改动。**
4. **铁律 D：宽松容错与降级兜底（Fail-Safe）**  
   - 状态栏数值标签采用宽容正则，即使 AI 漏闭合标签或格式轻微瑕疵，不阻断主状态解析与正文渲染。

### 3. 状态机解析与自动联锁逻辑（`状态机.js` 扩展伪代码）

```javascript
// 在 parseStatusBlock 中提取名器动作
function parseRelicAction(inner) {
  const m = inner.match(/<名器互动>([^<]+)<\/名器互动>/) || inner.match(/<名器互动>([^\n\r]+)/);
  if (!m) return null;
  // 解析出名器名称与动作类型（破身+1、内射+1、采补+1等）
  return extractAction(m[1]);
}

// 在 __xsdStateTick 状态机主循环中：
const action = parseRelicAction(statusBlock.raw);
if (action && action.relicId) {
  const cur = stat_data.relic_progress[action.relicId] || { stage: 1, infusion: 0, target: 5 };
  if (action.isInfusion && cur.stage === 1) {
    cur.infusion = Math.min(cur.target, cur.infusion + 1);
    // 阈值联锁：满额自动触发阶位开关
    if (cur.infusion >= cur.target) {
      stat_data.known[`${action.relicName}二阶段`] = true;
      cur.stage = 2;
      cur.infusion = 0; // 重置下一阶进度
      console.log(`[名器状态机] ${action.relicName} 浸润满额，自动激活二阶段！`);
    }
  }
}
```

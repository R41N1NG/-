# 工业级角色卡通用架构搭建规范

> 本文档基于高阶中控驱动型角色卡工程提炼而成，剥离所有特定题材背景与文案细节，专注于系统解耦、数据流转、世界书构建与状态机管控的通用工程架构。

---

## 一、 系统顶层四层解耦模型

该架构将一张复杂的角色卡解构为四个相互独立、职责清晰的层级，实现“机制由代码定、设定由世界书管、演理由大模型出、交互由状态栏承载”的分工：

```
┌────────────────────────────────────────────────────────┐
│ 1. 表现与交互层 (Presentation & UI)                    │
│    - Regex 脚本：捕获正文特定标签，替换为交互式 HTML    │
│    - 状态栏 (HUD)：实时展现时序、资源、人物状态与警报    │
│    - 动态网关 (Gateway)：第 0 楼身份与分支选择界面     │
├────────────────────────────────────────────────────────┤
│ 2. 状态机与中控层 (Engine & Extensions)                │
│    - 变量池 (Variables Pool)：状态数值与档案的单一真源 │
│    - 中枢脚本：时钟步进、数值检定、波次流转与台账同步   │
│    - GM 调试器：解耦挂载的后台修改与测试控制台        │
├────────────────────────────────────────────────────────┤
│ 3. 知识与生态层 (Character Book / Lorebook)            │
│    - 静态总纲：常驻物理法则、生活作息、动作与交互约束   │
│    - 场景空间：空间尺度、三维感官、生态法则（按需激活） │
│    - 角色双轨：心智因果条目 + 基础全案条目（变量宏注入）│
│    - 动态台账：成长记录、信物线索、局势走向（回注中控） │
├────────────────────────────────────────────────────────┤
│ 4. 主卡核心层 (Card Metadata Core)                     │
│    - Description：仅保留系统总纲与世界底层运转公约      │
│    - First Message：挂载开局网关标签，坚决不抢跑正文    │
│    - Personality / Scenario：极简索引，避免数据冗余   │
└────────────────────────────────────────────────────────┘
```

## 二、 主卡元数据字段规范 (Card Metadata)

### 1. Description（系统世界总纲）
* **职能**：确立不可动摇的客观环境公约与行为交互红线，不写具体的故事情节。
* **标准包含模块**：
  * **自由裁量权规范**：声明各 NPC 依自身生存诉求与性格行事；玩家输入仅代表主观期望，叙事者拥有推演自由，但严禁代玩家做重大决断。
  * **真实物理与损耗律**：明确生理机能限制（如体力衰减、创伤流血、食物与饮水消耗、视听感知遮蔽）。
  * **原住民沉浸规范**：严禁打破第四面墙，指代方式遵循场景视线规律。
  * **初见通名规范**：未自报家门或未见名牌文书前，严禁直呼其名，仅以相貌、服饰、特征相称。
  * **作息与生活律**：规定时间推移下的环境状态（如昼夜交替、开门闭户、光影明暗）。

### 2. First Message（开局信标）
* **职能**：作为引导入口，完全杜绝静态剧情预设。
* **标准构造**：
  * 仅包含特定的开局网关占位标签（如 `<system_gateway>`）；
  * 配合前端脚本在首楼动态渲染可交互选择面板，由玩家自主选择出生点、携带装备或初始身份。

### 3. Scenario & Personality
* **Scenario**：仅保留一句话的时空与局势定格（何时、何地、何种危机前夕）。
* **Personality**：仅收录核心登场者的简明行为倾向，主要数据转移至世界书与变量池。

## 三、 世界书分层构建法 (Character Book Architecture)

世界书按职能划分为四种不同特性的条目池，避免单次交互将全量数据塞入上下文：

### 1. 静态总纲层（Static World Laws）
* **配置参数**：`constant: true`（常驻）、`position: at_depth`。
* **内容构成**：
  * **时序作息律**：细化不同时段的环境变迁与常规行为模式；
  * **法则与交互约束**：伤害判定标准、资源获取上限、检定准则；
  * **演出风格指导**：文字留白戒律、肢体与情绪传递规范。

### 2. 场景空间层（Micro Spatial Scenes）
* **配置参数**：`constant: false`、由地名/关键词精准触发。
* **结构化书写模板**：
  ```
  [场景标识_空间名]
  空间格局: 建筑结构、出入口、遮蔽物、死角分布。
  感官氛围:
    - 视觉/光照: 光线来源、阴影盲区、能见度。
    - 声音: 背景噪音、脚步声传导、异常声响阈值。
    - 气味/温感: 环境气味、湿度、冷热触感。
  场域生态与交互法则:
    - 该区域的安全隐患、资源刷新点、行动限制规则。
  ```

### 3. 角色双轨条目（Two-Track Character Model）
为避免单个角色条目过大，每个 NPC 拆分为两个条目：
* **轨道 A · 角色心智（Mental State）**：
  * 包含深层生存动机、应对危险时的防御机制、崩溃或妥协的临界点；
  * 采用变量宏（如 `{{getvar::char_mental_id}}`）引入，便于动态刷新。
* **轨道 B · 角色全案（Profile & Stats）**：
  * 包含生理状态、装备栏、私藏物资、核心弱点；
  * 采用变量宏（如 `{{getvar::char_profile_id}}`）引入。

### 4. 动态台账层（Dynamic Feedback & Ledgers）
* **配置参数**：`constant: true`、插入深度适中。
* **职能**：将中控中实时变动的核心状态回注给大模型。
* **标准台账条目**：
  * **状态真值台账**：玩家当前健康度、技能状态、庇护所防御指数；
  * **信物与情报台账**：已经确认的线索、已收集的关键道具；
  * **局势流转台账**：当前周期轮次、怪物波次烈度、近期重大事件摘要。

## 四、 扩展层与中控数据工程 (Tavern Helper & Variables)

### 1. 状态单一真源原则 (Single Source of Truth)
大模型本身不直接负责记录数值的准确增减，数值真源存放于扩展变量池（Variables）中：
* 模型在正文输出中通过结构化标签（或自然语义行为）申报事实；
* 中控脚本解析申报事实，执行增减计算，更新变量池；
* 变量池数据通过状态栏展现，并通过世界书台账条目注入给下一轮提示词。

### 2. 变量池命名规范

> **适用范围声明（2026-11-07 补）**：本节为跨题材**通用示例命名**，仅示范「按域分组」的组织思路。怪谈楼层工程的实际命名以[《规范_真源裁定表.md》](规范_真源裁定表.md) 为准，统一收拢于 `apt_mvu` 命名空间，不使用下列 `sys_*` / `char_stat_*`。

* `sys_time_step`：周期步进与时钟；
* `sys_phase`：当前所处阶段（如：安全搜刮期 / 危险坚守期）；
* `char_stat_[id]`：各个角色的即时生理与心态数值；
* `base_defense_rating`：据点核心防御指数；
* `inventory_[target]`：玩家及各角色的持有清单。

**本项目对照**：`sys_time_step` → `apt_mvu.system.total_min`；`sys_phase` → `apt_mvu.system.phase`；`char_stat_[id]` → `apt_mvu.npcs[id]` 或 `apt_mvu.player`；`base_defense_rating` → `apt_mvu.world.nodes[room].door`；`inventory_[target]` → `apt_mvu.player.inventory` 或 `apt_mvu.npcs[id].holding`。

### 3. 三大核心脚本职责划分
* **核心态势感知脚本 (HUD & Engine Core)**：
  * 处理全局时序递进；
  * 监控危险周期的触发与事件播报；
  * 渲染屏幕端状态栏面板。
* **开局网关脚本 (Gateway Script)**：
  * 专职负责首楼交互界面的挂载与初始化参数派发；
  * 玩家做出选择后，将初始物资与背景写入变量池并触发首轮开局。
* **后台管理/调试器 (GM Editor Script)**：
  * 独立解耦的调试面板；
  * 允许在测试过程中实时查看、修改任意变量，方便快速校对数值平衡。

## 五、 渲染与展示规范 (Regex & UI)

1. **结构化标签与前端渲染分离**：
   * 正文中的系统广播、阶段转换、环境警报均包裹于自定义语义标签内（如 `<incursion_alert>`、`<status_block>`）；
   * 通过 Regex 脚本匹配这些标签，转化为具有视觉层级的美化卡片或动态面板。
2. **生命周期与防御守卫**：
   * DOM 注入严格采用“先判空、先清理旧节点、再挂载新闭包”模式，杜绝刷新残留与内存泄漏；
   * 脚本严禁因非核心视觉元素未找到而抛出阻断性异常。

---

## 六、 架构优势总结

1. **超低 Token 开销**：主卡极其精简，场景与角色全部按需加载，长程对话不臃肿。
2. **杜绝模型幻觉与数值崩坏**：核心状态由变量池锁死，大模型无法擅自增加资源或复活减员。
3. **零代打与沉浸感**：主卡与首楼完全交出控制权，留白给玩家操作，剧情走向由交互动态涌现。
4. **易维护与易扩展**：增减地图场景、添加新角色只需在世界书增添标准化模板条目，无需重构整卡逻辑。

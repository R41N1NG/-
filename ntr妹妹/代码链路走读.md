```
┌─────────────────────────────────────────────────────────┐

└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
```

## 二、时刻一：加载阶段

浏览器从上往下执行每个脚本，**先加载的必须先就位**，因为后面的要引用前面的。

### 2.1 `0_okh_boot.js`（30 行）

**这一刻做了一件事**：在 `window` 上挂一个空盒子。

```js
window.__OKH__ = {
  version: '0.1.0',
  modules: {},              // 后面每个模块往这里注册自己
  hooks: { afterTurn: [] }, // 钩子表，用于"通知"而非"调用"
  ready: false
}
```

**为什么需要它**：浏览器里没有 `import` 解析，模块之间没法直接互相引用。用全局对象做中转，是最稳的跨版本方案。

**它防了一件事**：重复初始化。

```js
if (window.__OKH__) { return }   // 已经有了就不重建
```

不防的话，热重载会把所有模块清空，正在跑的推演就断了。

**输出**：`window.__OKH__` 这个对象本身。

### 2.2 `1_okh_core.js`（142 行）

**这一刻做了一件事**：建立变量读写的唯一通道。

#### 关键：存储适配层

```js
const store = (function () {
  if (typeof getvar === 'function' && typeof setvar === 'function') {
    return { mode: 'tavern', get: k => getvar(k), set: (k, v) => setvar(k, v), ... }
  }
  // 退路：内存模式
  const mem = new Map()
  return { mode: 'memory', get: k => mem.get(k), set: (k, v) => mem.set(k, v), ... }
})()
```

**这一段是整份代码里最实用的设计。**

- 在酒馆里 → 用 `getvar`/`setvar`，数据进存档，刷新不丢
- 在 Node 里 → 用内存 Map，测试照跑

同一份代码两边都能用，**不用维护两套**。

#### `read(path, fallback)`

```js
function read(path, fallback = null) {
  const v = store.get(`okh.${path}`)
  return (v === undefined || v === null) ? fallback : v
}
```

- 自动加 `okh.` 前缀，避免和卡里别的变量撞名
- `null` 和 `undefined` 都当"没有"，返回 fallback

#### `write(path, value)` —— 带回读校验

```js
function write(path, value) {
  store.set(key, value)
  const back = store.get(key)
  const ok = JSON.stringify(back) === JSON.stringify(value)
  if (!ok) console.warn('[OKH] 写入校验失败：', path)
  return ok
}
```

**为什么要回读**：酒馆的 `setvar` 偶有静默失败——不报错，但也没写进去。不验的话，后面读出来是旧的，排查半天查不出。

**输出**：`read` / `write` / `has` / `remove` / `keys` / `dump` / `mode`

### 2.4 `3_okh_rules.js`（203 行）

**这一刻做了一件事**：建立纯函数判定层。**没有任何副作用**。

#### `test(value, expr)` — 条件表达式解析

```js
test(35, '>=30')   // → true
test(35, '<30')    // → false
```

支持 `<` `<=` `>` `>=` 四种。用于底线阈值、行动门槛、历史次数。

#### `lineActive(line, npc)` — 这条底线还在不在

```js
function lineActive(line, npc) {
  for (const [key, expr] of Object.entries(line.holdsWhile)) {
    const v = key === 'corruption' ? npc.corruption
            : key === 'sanity' ? npc.sanity
            : (npc.drives[key] ?? 0)
    if (!test(v, expr)) return false
  }
  return true
}
```

**返回 true = 底线还在 = 会封锁行动。**

举例：

```js
{ id: 'no_contact', type: 'no_physical_contact', holdsWhile: { corruption: '<30' } }
```

- `corruption = 20` → `test(20, '<30')` = true → **底线有效**
- `corruption = 35` → `test(35, '<30')` = false → **底线失效，解封**

#### `availableActions(npc, actionLibrary, ctx)` — 筛出能做的

这是**整个决策的第一道关卡**，做三件事：

```js
for (const aid of npc.actions) {
  const action = ... // 拿到行动定义（可能有个体覆盖）

  // ① 前置条件：阶段/时段/地点/驱动力/堕落度/标记/历史
  const chk = checkRequires(action, npc, ctx)
  if (!chk.ok) { rejected.push(...); continue }

  // ② 底线封锁：按"类型"匹配
  const hit = (action.blockedBy || []).filter(t => lineTypes.includes(t))
  if (hit.length) { blocked.push(...); continue }

  // ③ 通过
  ok.push(action)
}
```

**注意第 ② 步的匹配方式**：

```js
// 行动说：我被 no_physical_contact 这类底线封
action.blockedBy = ['no_physical_contact']

// 角色说：我有一条这个类型的底线
npc.lines = [{ id: 'no_contact', type: 'no_physical_contact', holdsWhile: {...} }]

// 匹配的是 type，不是 id
```

**为什么要按类型匹配**：不同角色可以给自己的底线起不同 id（`no_contact` / `keep_purity` / `dont_touch`），但只要 `type` 一样，就能封同一批行动。**角色配置自由，封锁规则统一。**

**输出**：`{ ok: [...], blocked: [...], rejected: [...] }` 三堆

- `ok`：能做的
- `blocked`：被底线挡的（调试时要看）
- `rejected`：条件不够的（调试时要看）

### 2.5 `4_okh_agency.js`（191 行）

**这一刻做了一件事**：决策层。**它自己不做任何判定，全靠 rules**。

#### 配置表（数据驱动）

```js
const CONFIG = {
  inertiaPerRepeat: 0.25,   // 每重做一次 +25%
  inertiaCap: 4,            // 惯性上限（最多 +100%）
  idlePerTurn: 0.15,        // 每闲置一回合 +15%
  idleCap: 6,               // 闲置上限（最多 +90%）
  noiseRange: 0.20          // 随机扰动 ±20%
}

const TAG_RULES = [
  { tag: 'money',     drive: 'need',      op: '>', val: 60, mult: 1.40 },
  { tag: 'expose',    drive: 'shame',     op: '>', val: 60, mult: 0.75 },
  { tag: 'risk',      drive: 'curiosity', op: '>', val: 60, mult: 1.35 },
  { tag: 'risk',      drive: 'fear',      op: '>', val: 65, mult: 0.70 },
  { tag: 'duty',      drive: 'duty',      op: '>', val: 65, mult: 1.25 },
  { tag: 'bond',      drive: 'loyalty',   op: '>', val: 65, mult: 1.25 },
  { tag: 'humiliate', drive: 'pride',     op: '>', val: 70, mult: 0.60 },
  { tag: 'risk',      drive: null,        op: 'sanity<', val: 40, mult: 1.20 }
]
```

**为什么是表不是 if 链**：加一条规则只加一行数据，不动代码逻辑。这是"改起来方便"的核心。

#### `tagModifier(action, npc)` — 算修正系数

```js
for (const rule of TAG_RULES) {
  if (!tags.includes(rule.tag)) continue          // 行动没这个标签，跳过

  const value = isSanity ? npc.sanity : (d[rule.drive] ?? 0)
  if (cmp(value, op, rule.val)) {
    mult *= rule.mult
    notes.push(`${rule.tag}:${rule.drive}${rule.mult}`)   // 记下来，调试用
  }
}
```

**`notes` 数组很重要**：它记录了每一项修正，调试时能看到"为什么这个行动分这么高"。

#### `scoreOf(action, npc, rnd)` — 完整打分

```js
const count  = hist.filter(h => h === action.id).length      // 做过几次
const idle   = ...                                            // 多久没做
const inertia = 1 + 0.25 * Math.min(count, 4)                 // 惯性加成
const idleBoost = 1 + 0.15 * Math.min(idle, 6)                // 闲置补偿
const { mult } = tagModifier(action, npc)                     // 标签修正
const noise = 0.8 + rnd * 0.4                                 // ±20% 噪声

const score = action.base * mult * inertia * idleBoost * noise
```

**五个乘数，每个都有明确作用**：

| 乘数 | 作用 | 上限 |
|---|---|---|
| `base` | 这个行动本身的吸引力 | 配置里定 |
| `mult` | 当前状态下该不该更想做 | 无（但规则有限） |
| `inertia` | 做过的事更容易再做 | +100% |
| `idleBoost` | 很久没做的事更有吸引力 | +90% |
| `noise` | 保留不确定性 | ±20% |

**惯性和闲置必须成对**：只有惯性会锁死，只有闲置会乱跳。

#### `decide(npc, actionLibrary, ctx, rndFn)` — 完整决策

```js
function decide(npc, actionLibrary, ctx, rndFn = Math.random) {
  // ① 筛
  const { ok, blocked, rejected } = rules().availableActions(npc, actionLibrary, ctx)
  if (!ok.length) return { action: null, ... }

  // ② 打分
  const scored = ok.map(a => ({ ...scoreOf(a, npc, rndFn()), action: a }))
                   .sort((x, y) => y.score - x.score)

  // ③ 加权随机
  const chosen = pickWeighted(scored, rndFn())

  return { action: chosen?.action || null, scored, blocked, rejected, chosen }
}
```

**第 ③ 步是关键**：不是取最高分，是**按分数占比抽签**。

```js
function pickWeighted(scored, rnd) {
  const total = scored.reduce((s, c) => s + c.score, 0)
  const target = rnd * total
  let acc = 0
  for (const c of scored) {
    acc += c.score
    if (target <= acc) return c
  }
}
```

**为什么不取最高分**：取最高分的话，同样的状态下永远做同一件事，角色就变成可预测的机器了。加权随机保留了"人"的不确定性——高分的事更常发生，但不是必然。

**输出**：`{ action, scored, blocked, rejected }`

`scored` 里的每一项都带完整打分明细，调试全靠它。

### 2.6 `5_okh_presence.js`（140 行）

**这一刻做了一件事**：出场判定。**四闸门串联，对外只吐在场名单**。

#### `checkOne(npc, ctx)` — 单个角色过四道门

```js
function checkOne(npc, ctx) {
  // 闸门 0：缺席规则（优先级最高）
  const abReason = absenceReason(npc, ctx.flags)
  if (abReason) return { pass: false, gate: 0, reason: abReason, absentReason: abReason }

  // 闸门 1：空间
  if (npc.location !== ctx.roomId) {
    return { pass: false, gate: 1, reason: `在 ${npc.location}` }
  }

  // 闸门 2：日程
  const allow = npc.schedule?.[ctx.phase]
  if (allow && !allow.includes(npc.location)) {
    return { pass: false, gate: 2, reason: `${ctx.phase} 不该在 ${npc.location}` }
  }

  // 闸门 3：剧情
  for (const [k, v] of Object.entries(req.flags || {})) {
    if (ctx.flags?.[k] !== v) return { pass: false, gate: 3, ... }
  }

  return { pass: true }
}
```

**闸门 0 为什么在 1 前面**：缺席规则（被软禁、已离镇）要压过一切。不这么排的话，一个被关起来的人只要地点碰巧对上就能出场。

#### `resolve(npcs, ctx)` — 全员过门 + 排序 + 限流

```js
// ① 全员过门
for (const npc of npcs) {
  const r = checkOne(npc, ctx)
  if (!r.pass) { 分到 absent 或 rejected }
  else candidates.push(npc)
}

// ② 闸门 4：排序
candidates.sort((a, b) => {
  const pa = a.priority ?? 1, pb = b.priority ?? 1
  if (pb !== pa) return pb - pa                      // 优先级高的先上
  const sa = lastSeen[a.id] ?? -999                  // 同优先级看谁久没出场
  const sb = lastSeen[b.id] ?? -999
  return sa - sb
})

// ③ 限流
const onStage = candidates.slice(0, CONFIG.maxOnStage)   // 默认 3 人
const offStage = candidates.slice(CONFIG.maxOnStage)
```

**为什么要限 3 人**：LLM 的注意力有限。五个角色同时在场，文笔质量会明显下降；只留三个，反而能写透。

**为什么排序要看"久没出场"**：不然优先级低的角色永远轮不到，玩家会忘了还有这个人。

**输出**：`{ present, offStage, absent, rejected }`

- `present`：真正的在场名单（≤3）
- `offStage`：过了闸门但被挤出画面的
- `absent`：因缺席规则不在的
- `rejected`：被闸门 1/2/3 挡的

### 2.8 `7_okh_turn.js`（303 行）

**这一刻做了一件事**：主循环。**它不认识任何角色，只负责串联**。

#### 关键设计：延迟取依赖

```js
function dep(name) {
  const m = REG.modules[name]
  if (!m) throw new Error(`[OKH] 依赖未加载：${name}（检查脚本顺序）`)
  return m
}
```

**不在加载时解构**：

```js
// ❌ 危险写法
const { core, schema } = REG.modules

// ✅ 安全写法
const core = dep('core')
```

**差别**：加载时解构，如果顺序错了拿到 `undefined`，后面调用时才炸，而且报错信息跟真正原因无关。延迟取的话，**顺序错了当场就说缺谁**。

#### `parseElapsed(text)` — 从 AI 回复里抠时间

```js
function parseElapsed(text) {
  const m = /<time[^>]*\belapsed\s*=\s*"(\d+)"/i.exec(text)
  if (!m) return null
  const n = Number(m[1])
  return Number.isFinite(n) && n >= 0 && n <= 1440 ? n : null
}
```

- 匹配 `<time elapsed="30" ... />`
- 超过 1440 分钟（一天）视为异常，返回 null

#### `tick(elapsedMin)` — 推时间，可能触发推演

```js
function tick(elapsedMin) {
  const before = core.read('sys.total_min', 0)
  const after = before + elapsedMin
  core.write('sys.total_min', after)

  const oldPhase = core.read('sys.phase', null)
  const newPhase = derivePhase(after)
  core.write('sys.phase', newPhase)

  // 只有跨时段才推演
  if (oldPhase !== null && oldPhase !== newPhase) {
    return runTurn()
  }
}
```

**为什么跨时段才推演**：每来一条消息就推演一次，会太频繁。人一天也就吃三顿饭，不是每句话都发生大事。

#### `runTurn()` — 核心，一轮完整推演

```js
function runTurn(opts = {}) {
  const core = dep('core'), agency = dep('agency'), ...   // ① 取依赖

  const npcs = core.read('npcs', {})                        // ② 读状态
  const actions = core.read('actionLibrary', {})
  const phase = core.read('sys.phase', 'morning')

  for (const [id, npc] of Object.entries(npcs)) {           // ③ 逐个角色
    const res = agency.decide(npc, actions, { phase, flags }, rndFn)

    if (res.action) {
      events.push(applyAction(npc, res.action))             // ④ 结算
    }

    endOfTurnDrift(npc)                                     // ⑤ 漂移
    npc.stage = schema.stageOf(npc.corruption)              // ⑥ 更新阶段
    translate.writeCharD1(id, npc, core.read, core.write)   // ⑦ 转文本
  }

  const pres = presence.resolve(...)                        // ⑧ 算在场

  core.write('npcs', npcs)                                  // ⑨ 写回
  core.write('present', ...)
  ...

  for (const fn of REG.hooks.afterTurn) fn(_lastReport)     // ⑩ 通知
  core.write('ledger', buildLedger(_lastReport))            // ⑪ 写台账
}
```

**这十一行，就是整个系统的心脏。**

#### `applyAction(npc, action)` — 结算

```js
for (const [k, v] of Object.entries(action.effects.drives || {})) {
  npc.drives[k] = Math.max(0, Math.min(100, (npc.drives[k] ?? 0) + v))
}
npc.corruption = Math.max(0, Math.min(100, npc.corruption + (action.effects.corruption || 0)))
npc.sanity = ...
npc.exposure = ...
if (action.effects.move) npc.location = action.effects.move
npc.history = (npc.history || []).concat(action.id).slice(-30)
```

**所有数值都被 `Math.max(0, Math.min(100, ...))` 夹紧**，不会出现负数或超过 100 的脏数据。

`history` 只留最近 30 条，防止无限增长。

#### `endOfTurnDrift(npc)` — 每轮漂移

```js
for (const k of Object.keys(npc.drives)) {
  const base = npc.baseline?.[k] ?? npc.drives[k]
  npc.drives[k] += (base - npc.drives[k]) * 0.10     // 向基线回归 10%
}
if ('need' in npc.drives) {
  npc.drives.need = Math.min(100, npc.drives.need + 2)   // 生活开销
}
```

**两件事**：

1. **回归**：驱动力每轮向基线靠 10%，防止一次性资源（如好奇）用完就死
2. **压力**：`need` 每轮 +2，形成"钱永远不够"的持续压力

#### `buildLedger(report)` — 生成给 AI 的台账

```js
lines.push(`【第 ${day} 天 · ${phaseName}】`)
lines.push('在场：' + ...)
lines.push('近况：')
for (const e of recent.slice(-3)) lines.push('· ' + e.narration)
```

**限制 3 条近况**，防止吃 token。

输出长这样：

```
【第 3 天 · 夜晚】
在场：古兰（抱臂站着）、妮丝（金发双马尾）
近况：
· 奥萝拉去接了份工，忙到很晚才回来。
· 妮丝在集市上摆了半天的摊。
```

#### `onMessageReceived()` — 事件钩子

```js
function onMessageReceived() {
  const ctx = SillyTavern.getContext()
  const last = ctx.chat[ctx.chat.length - 1]
  if (!last || last.is_user) return           // 只处理 AI 的消息

  const elapsed = parseElapsed(last.mes || '')

  if (elapsed === null) {
    // 兜底：AI 没申报时间
    if (++_msgCount >= 5) { _msgCount = 0; tick(20) }
    return
  }

  _msgCount = 0
  tick(elapsed)
}
```

**兜底机制**：AI 有时候不输出 `<time>`，这时候每 5 轮补 20 分钟，保证世界还会慢慢走。

## 三、时刻三：一次完整回合的详细追踪

场景：玩家说「我去找奥萝拉」，AI 回复里带 `<time elapsed="240" />`。

### 步骤 1 · 钩子触发

```
MESSAGE_RECEIVED
  ↓
onMessageReceived()
  ↓
const last = ctx.chat[ctx.chat.length - 1]
if (last.is_user) return          // 是玩家发的，跳过
```

### 步骤 2 · 抠时间

```
parseElapsed('<time elapsed="240" end="1日10:00" />')
  ↓ 正则匹配
240
```

### 步骤 3 · 推时间

```
tick(240)
  ├─ before = 360
  ├─ after  = 600
  ├─ oldPhase = 'morning'
  ├─ newPhase = derivePhase(600) = 'afternoon'   ← 变了！
  └─ 触发 runTurn()
```

### 步骤 4 · 逐个角色决策（以奥萝拉为例）

```
agency.decide(aurora, actionLibrary, { phase: 'afternoon', flags })
  │
  ├─ rules.availableActions(aurora, lib, ctx)
  │    ├─ work_shift    ✅ need=75 > 50，通过
  │    ├─ pray          ✅ 无条件，通过
  │    ├─ serve         ❌ 被 no_physical_contact 挡住（corruption 15 < 30）
  │    ├─ conceal       ❌ corruption 15 < 20，条件不足
  │    └─ ...
  │    返回 { ok: [8项], blocked: [1项], rejected: [2项] }
  │
  ├─ scoreOf 逐项打分
  │    work_shift:  28 × 1.4(need) × 1.0(惯性) × 1.9(闲置) × 0.99 = 73.7
  │    pray:        24 × 1.2(duty) × 1.0        × 1.9        × 1.05 = 57.5
  │    care:        22 × 1.2(duty) × 1.25       × 1.0        × 1.01 = 33.3
  │    ...
  │
  └─ pickWeighted(scored, rnd=0.31)
       总分 = 280
       target = 0.31 × 280 = 86.8
       累加：73.7（不够）→ 131.2（够了！）
       命中 pray
```

### 步骤 5 · 结算

```
applyAction(aurora, pray)
  ├─ drives.shame  -6  → 65-6 = 59
  ├─ drives.duty   +3  → 70+3 = 73
  ├─ drives.fear   -3  → 50-3 = 47
  ├─ sanity        +3  → 80+3 = 83
  ├─ corruption    +0  → 15（不变）
  └─ history.push('pray')
```

### 步骤 6 · 漂移

```
endOfTurnDrift(aurora)
  ├─ duty:   73 + (70-73)×0.1 = 72.7    ← 向基线回归
  ├─ shame:  59 + (65-59)×0.1 = 59.6
  ├─ need:   58 + 2 = 60                ← 生活开销
  └─ ...
```

### 步骤 7 · 阶段与时区检查


### 步骤 8 · 转文本

```
  │
  ├─ 奥萝拉: location=church ✅ → 日程 afternoon 允许 church ✅ → 通过
```

一个字段从生到死，经过哪些模块：

## 五、三个关键设计点

### 5.1 判定与结算分离

```
rules.availableActions  →  只说"能不能做"     （纯函数，无副作用）
applyAction             →  才真正改状态        （有副作用）
```

**好处**：规则可以单独测、单独改。想知道"她为什么不能做这件事"，调 `rules.explain()` 就行，不用担心中途改了状态。

### 5.2 数字与文本分离

```
corruption = 35              ← 只在系统内部流通
       ↓ translate
"她开始找理由晚归..."        ← 只有这个给 AI 看
```

**为什么**：AI 看到数字会"演数字"，写出"她的堕落度提升了"这种鬼话。看到描述才会写戏。

### 5.3 通知与调用分离

```
❌ turn 直接调 hud.render()
✅ turn 通知 hooks，hud 自己订阅
```

**好处**：`hud` 可以随时拔掉，`turn` 不受影响。以后想加个"推演完后发通知"的模块，注册个钩子就行，`turn` 不用改。

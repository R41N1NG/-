## 一、范例卡不可动的契约

先钉死哪些东西不能碰，后面所有设计都绕着它们走。

### 1.1 双层闭合

```xml
<content>纯文学叙事正文</content>
<status_bar>结构化数据申报，文末有且仅有一个</status_bar>
```

**不可改。** 任何新增信息都必须落在这两个块里，或者落进变量池。不能出现第三个顶层块。

### 1.2 状态栏标签全集（封闭）

```xml
<time elapsed end />
<move to noise />
<door state />
<injury level type />
<heal target item />
<loot item />
<eliminate target cause />
<acquire_key fragment />
<focus npc />
<npc_mind>…</npc_mind>
<threat_radar>…</threat_radar>
<supply_radar>…</supply_radar>
```

**不可增删。** 这一组已经覆盖了时空、位移、门、伤、治疗、拾取、减员、线索、焦点、内心、声光异象。

### 1.3 四层解耦

```
表现与交互层（Regex / HUD / 网关）
状态机与中控层（变量池 / 中枢脚本 / 调试器）
知识与生态层（世界书四池）
主卡核心层（Description / First Message / Scenario）
```

**不可加减层。** 我的系统只能是「状态机与中控层」里的一部分逻辑，不能自成一层。

### 1.4 角色三层切片

```
char_census_{id}   ~80 字    常驻名单
char_d1_{id}       200~300 字 心智涌现指南
char_d3_{id}       800~1000 字 全案档案
```

**不可改结构。** 想加内容，只能往这三个变量的文本里塞。

## 三、四闸门降级为内部算法

v0.1 把四闸门当"设计亮点"写进文档，但**它根本不该出现在契约层**——它只是脚本内部算 `present` 字段的过程。

```
脚本内部（玩家与 LLM 都看不见）：
  for npc:
    if npc.room_id !== player.room_id: continue
    if !scheduleAllows(npc, phase): continue
    if !storyAllows(npc, flags): continue
    candidates.push(npc)
  present = candidates.sort(priority).slice(0, MAX)

对外（唯一输出点）：
  HUD【在场】← present
```

**对外零暴露。** 不产生新标签，不产生新变量，不产生新条目。

闸门本身保留，因为它是逻辑，不是契约。改了也不影响范例卡。

## 四、堕落度怎么进范例卡（关键）

这是最难的一处。范例卡的心智是**描述性的**（`char_d1` 是自然语言段落），而我的 agency 是**数值化的**（`corruption: 0-100`）。

### 4.1 不能做的

```
❌ 直接往 char_d1 里塞 "corruption: 35"
   原因：char_d1 是给 LLM 读的叙事性文本，塞数字会破坏文风
   且 LLM 会开始"演数字"，而不是"演人"
```

### 4.2 要做的：数值 → 文本翻译层

```
数值状态                     翻译后的 char_d1 片段
─────────────────────────────────────────────────
corruption 0-29  → 「她最近总是很晚才回来，问起只说活多。」
corruption 30-54 → 「她开始避开伯里的目光，说话时会突然停住。」
corruption 55-79 → 「她已经不太解释了，只是把挣来的钱放下就走。」
corruption 80-100→ 「她不再提以前的事，仿佛那些从没发生过。」
```

**同一套模板，按区间替换。** 这是纯文本操作，不碰任何契约。

### 4.3 为什么这样是对的

范例卡的哲学是「**机制由代码定、设定由世界书管、演理由大模型出**」。

堕落度是机制，属于代码；但它对 LLM 的呈现必须是设定文本，属于世界书。

所以正确的链路是：

```
agency 算 corruption（机制层，代码）
       ↓ 翻译
char_d1_{id} 的文本（设定层，世界书）
       ↓ {{getvar::char_d1_id}}
世界书条目 A（LLM 看到的是描述，不是数字）
```

**LLM 永远不会看到 `corruption: 35`，它只会看到「她开始避开伯里的目光」。**

这正是范例卡的设计意图：让模型演人，不让模型算数。

## 五、时间推进怎么对齐

范例卡已经有 `<time elapsed="30" end="1日08:30" />`，`elapsed` 是分钟数。

### 5.1 不做第二套时间

```
❌ v0.1 设计：agency 自己维护「日 + 时段」
✅ v0.2 修正：直接读 apt_mvu 的时间真值，时段由分钟数换算
```

换算表：

| phase | 分钟区间 |
|---|---|
| `morning` | 06:00 – 10:00 |
| `afternoon` | 10:00 – 17:00 |
| `night` | 17:00 – 23:00 |
| `deep_night` | 23:00 – 06:00 |

**`total_min` 是唯一真源**，`phase` 是派生视图。这和范例卡「单一真源 + 只读派生」的规矩一致。

### 5.2 推进时机

```
每轮对话结束 → 解析 <time elapsed>
             → total_min += elapsed
             → 若跨过时段边界，触发 agency 推演
```

**推演由时间驱动，不由回合数驱动。** 这样和范例卡完全同频。

## 六、命名怎么定（不能用 apt_mvu）

### 6.1 为什么不能用

`角色卡通用架构搭建规范.md` 第 115 行写得很清楚：

> 本节为跨题材**通用示例命名**，仅示范「按域分组」的组织思路。怪谈楼层工程的实际命名以《规范_真源裁定表.md》为准，统一收拢于 `apt_mvu` 命名空间。

`apt_mvu` 是**怪谈楼层（公寓）项目**的命名空间，属于那个项目的真源裁定表。

### 6.2 通用规范给的写法

```js
sys_time_step           → 周期步进与时钟
sys_phase               → 当前阶段
char_stat_[id]          → 各角色即时状态
inventory_[target]      → 持有清单
```

这套 `sys_*` / `char_stat_*` 是**跨题材通用示例**，正是我们该照着定的。

### 6.3 本项目命名建议

按域分组的思路，起一个本项目的前缀。建议 **`okh_`**（奥克赫斯）：

```js
okh_sys.total_min          // 时间真源（对齐 sys_time_step）
okh_sys.phase              // 派生视图（对齐 sys_phase）
okh_player.room_id         // 玩家位置
okh_player.flags           // 玩家侧剧情标记
okh_npc_{id}.room_id       // 角色位置（对齐 char_stat_[id]）
okh_npc_{id}.alive         // 存活
okh_npc_{id}.flags         // 角色剧情标记
okh_world.flags            // 世界级标记
```

**只保留范例卡需要的东西，不把 agency 的内部数值也倒出来。**

> 待主人确认前缀。若主人想沿用别的命名，改一个词的事。

## 七、时序对齐：脚本先跑，LLM 后演

```
① [脚本] 解析上一轮 <time elapsed> → total_min += elapsed
② [脚本] 若跨时段边界：
        agency 推演（每个角色选一个行动，含移动）
          ↓
        写 okh_npc_{id}.room_id
          ↓
        翻译 corruption → 覆盖 char_d1_{id} 文本
③ [脚本] 算 present（四闸门，内部）
          ↓
        渲染 HUD【在场】（已有字段）
④ [LLM ] 读上下文（世界书台帐 + char_d1 宏）
        生成 <content>，按需申报 <status_bar>
⑤ [脚本] 解析申报，合并进变量池
⑥ [脚本] 渲染 HUD
```

**关键：第①②③步全部在 LLM 看到提示词之前完成。** LLM 拿到的已经是"世界此刻的样子"。

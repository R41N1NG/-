不使用未经推导的经验数字作为红线；确需数量阈值的，标 🟡 并说明用途是「触发复核」而非「判定合格」。

## 零、定义

### 0.1 「分模块耦合」的准确定义

两个要件同时成立，缺一不算：

| 要件 | 含义 | 判定方式 |
|---|---|---|
| **分模块** | 每个文件只有一个职责，且能用一句话说清 | 见 0.3 职责描述检验 |
| **耦合** | 模块之间只通过声明的接口通信 | 改一个模块内部实现，不需要动其他模块 |

**三个反例**（都不算分模块耦合）：

- 一个大文件用注释分成「解析区 / 规则区 / 界面区」——仍是单体
- 拆成多文件但 A 直接读写 B 的模块级变量——拆了没用
- 模块之间形成循环依赖——不是耦合，是缠绕

### 0.2 「状态机」范围

指角色卡的**后台运行逻辑**：变量读写、状态维护、输出解析、条件判定、数值结算、存档与迁移、界面同步、日志调试。

### 0.3 职责描述检验（可执行）

> 每个模块必须能用**一个名词短语**说清职责，例如「状态容器」「输入解析器」「结算器」。

判定方法：

1. 所有模块的职责短语列出来
2. 检查两两之间是否出现**重复的核心词**
3. 出现重复 → 职责重叠，边界画错，必须重新划分

例：
```
sm_core    → 状态容器
sm_parse   → 输入解析器
sm_rules   → 规则判定器
sm_effect  → 结算执行器
```
「状态容器」与「结算执行器」无重叠词 ✅
若出现「状态管理器」和「状态容器」，重复「状态」 → 边界错误 ❌

```
项目根/
├─ 角色卡制作规范.md              ← 本文件
├─ 状态机_模块注释模板.md
├─ 状态机_变更记录.md
├─ 状态机_架构说明.md
├─ scripts/
│  └─ check-deps.js              ← 依赖方向扫描（见 2.5）
└─ src/
   ├─ state/                     ← 按需创建，不建空文件
   ├─ state_index.js             ← 装配入口（唯一认识全部模块的地方）
   └─ _archive/                  ← 废案存放，永不删除
```

**按需创建原则**：下方是**职责清单**，不是必建文件表。项目不需要的模块就不建，不建空壳。

| 职责 | 建议文件名 | 是否需要 |
|---|---|---|
| 状态容器（读写、订阅、快照） | `sm_core.js` | 必需 |
| 数据结构定义、校验、默认值 | `sm_schema.js` | 有状态结构则必需 |
| 输入解析 | `sm_parse.js` | 有外部输入则必需 |
| 规则判定 | `sm_rules.js` | 有判定逻辑则必需 |
| 结算执行 | `sm_effect.js` | 有状态变更则必需 |
| 存档与迁移 | `sm_persist.js` | 有持久化则必需 |
| 界面渲染 | `sm_ui.js` | 有界面则必需 |
| 日志调试 | `sm_log.js` | 有调试需求则必需 |

**废案目录说明**：旧代码不是垃圾，是决策记录。三个月后想不起为什么这么写的时候，它是唯一的证据。**永不删除。**

## 二、🔴 模块划分规范

### 2.1 划分原则（三条，均为红线）

**原则一：一文件一职责**

> 一个文件只回答一个问题。判断标准是 0.3 的职责描述检验——不是数行数，不是数职责个数。

**原则二：变更同源性**

> 改 A 必须同时改 B，说明 A 和 B 应属同一模块。
> 改 A 从不触及 B，说明它们应分开。

检验方法（可执行）：翻最近三次变更记录，看是否存在「改 X 顺手改 Y」的固定搭配。有且反复出现 → 边界画错。

**原则三：依赖单向**

> 依赖箭头只能向下，禁止反向与越级。

允许的层级顺序（上层可依赖下层，反之禁止）：

```
log / core          ← 最底层，零依赖
  ↓
schema / persist
  ↓
parse
  ↓
rules
  ↓
effect
  ↓
ui                  ← 最上层
```

`core` 与 `log` **零依赖**：它们不知道任何其他模块存在。

### 2.2 各职责的禁止事项

| 职责 | 禁止做的事 |
|---|---|
| 状态容器 | 不解析、不判定、不渲染 |
| 数据定义 | 不做业务逻辑 |
| 输入解析 | **不改状态** |
| 规则判定 | **不执行结算**（必须是纯函数，无副作用） |
| 结算执行 | 不碰界面 |
| 存档迁移 | 不碰业务逻辑 |
| 界面渲染 | **不写业务状态** |
| 日志 | 不依赖任何业务模块 |

**判定与结算必须分离**：`rules` 只说「会发生什么」，`effect` 才让它发生。这样规则能单独测、单独改，不担心污染状态。

### 2.3 接口契约

每个模块导出同一套形状：

```js
export default {
  id: 'sm_effect',                    // 与文件名一致
  deps: ['core', 'schema', 'rules'],  // 声明依赖，由扫描脚本校验
  init(ctx) {},                       // 装配回调
  api: { apply() {}, preview() {} }   // 唯一对外接口
}
```

`version` 字段可选，不再强制。

**模块外只能调 `api` 里的方法。** 不能 import 模块的私有函数，不能读写模块级变量。

### 2.4 装配入口

`state_index.js` 是唯一允许认识全部模块的地方。模块之间不互相 import，全部通过 `ctx` 注入。

```js
// ✅ 正确：模块内部从 ctx 拿依赖
export default {
  id: 'sm_effect',
  deps: ['core', 'rules'],
  init(ctx) { this._core = ctx.core; this._rules = ctx.rules },
  api: { apply() { /* 用 this._core */ } }
}
```

```js
// ❌ 错误：模块之间直接 import
import rules from './sm_rules.js'   // 越级 + 绕过注入
```

### 2.5 🔴 依赖校验的真实做法

**必须明确：`deps` 声明本身没有运行时强制力。**

ES module 的 `import` 是编译期静态解析的，运行时的 `init(ctx)` 拦截不住已经 import 进来的模块。所以校验只能靠静态扫描：

```js
// scripts/check-deps.js 的逻辑
// 1. 扫每个文件的 import 语句，提取被引用模块名
// 2. 对照层级白名单，判断是否越级或反向
// 3. 输出违规清单，非空则退出码 1

层级白名单：
  sm_core    → []
  sm_log     → []
  sm_schema  → ['core']
  sm_persist → ['core', 'schema']
  sm_parse   → ['core', 'schema']
  sm_rules   → ['core', 'schema']
  sm_effect  → ['core', 'schema', 'rules']
  sm_ui      → ['core', 'schema']
```

规范里写清这条，是为了避免一个误解：**「我声明了 deps，所以架构安全」是假的。** 声明只是文档，扫描才是护栏。

### 2.6 数据流

```
外部输入 → parse → 结构化对象 → rules 判定（纯函数，无副作用）
                                    ↓
                              判定结果 → effect 结算 → core 写入
                                                          ↓
                                                   core 订阅者 → ui 渲染
```

只允许这一套。不允许「ui 自己算一遍」「rules 直接写状态」这类旁路。

## 三、🟡 命名规范

| 对象 | 规则 | 示例 |
|---|---|---|
| 模块文件 | `sm_<职责>.js` | `sm_effect.js` |
| 模块 id | 与文件名一致 | `'sm_effect'` |
| 模块内私有函数 | `_` 前缀 | `_calcDamage()` |
| 对外接口 | 动词开头，不加前缀 | `apply()`, `preview()` |
| 状态字段 | 大写下划线分组 | `HP_CUR`, `SKILL_1` |
| 事件名 | `模块:动作` | `'effect:applied'` |
| 常量 | 全大写下划线 | `MAX_ROUND` |

**禁止**：
- 拼音命名
- **跨函数传递的**单字母变量（局部回调参数不受限：`arr.map(e => e.id)` 合法）
- 含义不明的缩写（`tmp`、`data2`、`obj1`）

## 四、注释规范

### 4.1 模块头注释（分级填写）

```js
/**
 * @module      sm_effect
 * @updated     2026-11-08 06:12
 * @status      active
 * @reason      用户反馈治疗量不随等级成长，改为走 ATK 系数
 * @deps        ['core', 'schema', 'rules']
 * @provides    { apply, preview }
 * @version     1.3.0
 * @history     见 状态机_变更记录.md#sm_effect
 */
```

| 级别 | 字段 | 说明 |
|---|---|---|
| 🔴 **必填** | `@module` | 模块标识 |
| 🔴 **必填** | `@updated` | 真实修改时间，精确到分钟 |
| 🔴 **必填** | `@status` | `active` / `deprecated` / `legacy` / `archived` |
| 🔴 **必填** | `@reason` | **说「为什么」，不说「做了什么」** |
| 🟡 按需 | `@deps` | 有依赖时必填 |
| 🟡 按需 | `@provides` | 有对外接口时必填 |
| 🟡 可选 | `@version` | 有版本管理需求时填，不强制语义化 |
| 🟡 可选 | `@history` | 有变更记录时填 |

**`@reason` 正反例**

| ❌ 说做了什么 | ✅ 说为什么 |
|---|---|
| 加了治疗分支 | 用户反馈治疗量不随等级成长，改为走 ATK 系数 |
| 修了 bug | 旧存档缺字段导致读档崩溃，补默认值兜底 |
| 重构 | rules 里混了写状态的逻辑，拆出来后规则才能单测 |

### 4.2 函数注释

导出函数、有副作用函数、参数超过两个的函数、返回结构复杂的函数——**必须**写：

```js
/**
 * 结算一次技能效果并写回状态
 * @param {string} actor  施法者 id
 * @param {string} skill  技能 id
 * @returns {{ok:boolean, delta:Object, reason?:string}}
 * @throws 不抛异常，失败统一走 ok:false
 */
```

一句话辅助函数可省略：`const _clamp = v => Math.max(0, Math.min(v, 1))`

### 4.3 🔴 四类强制行内注释

| 情况 | 要求 | 示例 |
|---|---|---|
| 魔法数字 | 说明来源与依赖 | `// 1.5 = 治疗系数，与伤害系数 1.0 刻意分开` |
| 边界判断 | 说明为什么这样判 | `// HP 归零不立即判死，留一回合救援窗口` |
| 兼容分支 | 说明为什么兜底 | `// 老存档无该字段，按 1 兜底；不能写 0 会除零` |
| 反向 / 特殊逻辑 | 说明为什么不能改 | `// 必须倒序：内部会 splice，正序会跳项` |

### 4.4 禁止的注释

- 🔴 复述代码的废话：`// 把 a 赋值给 b`
- 🔴 注释掉的死代码：要留就归档，不留就删
- 🔴 过期注释：改了代码没改注释，比没注释更糟

## 五、🔴 变更记录

### 5.1 三要素

| 要素 | 格式 | 不合格 |
|---|---|---|
| 修改时间 | `YYYY-MM-DD HH:mm` | 今天、刚才、11-8 |
| 修改理由 | 触发原因：用户反馈 / bug / 需求变更 / 重构 | 优化、调整、改了下 |
| 状态 | 四态之一 | 空着 |

### 5.2 状态四态

| 状态 | 含义 | 位置 |
|---|---|---|
| `active` | 当前版本，正常维护 | `src/state/` |
| `deprecated` | 能跑，已被替代，不再加功能 | 原位置，标注替代者 |
| `legacy` | 仅为兼容旧存档保留 | `src/_archive/` |
| `archived` | 完全废弃 | `src/_archive/` |

### 5.3 废案处理四步

1. **标记**：补 `@deprecated_since`、`@deprecated_why`、`@replaced_by`
2. **迁移**：移入 `src/_archive/`，文件名带版本与日期
3. **登记**：变更记录废案表加一行
4. **留痕**：新模块 `@reason` 写明替代了谁、为什么

废案表「废弃理由」一栏：**不能写「换成新的了」**，要写清旧的哪里不行。

## 六、🟡 代码复杂度指标

**不数行，数结构。** 以下三个指标可用工具算出，是本规范唯一允许的数量阈值：

| 指标 | 阈值 | 超限处理 |
|---|---|---|
| 函数嵌套深度 | > 4 层 | 拆函数 |
| 单函数分支数 | > 8 个 | 拆函数或改表驱动 |
| 圈复杂度 | > 15 | 重构 |

### 文件行数的定位（🟡 触发复核，非红线）

> **单文件超过 600 行 → 触发复核**，需在架构说明的「关键设计决策」里写清为什么不能拆。

理由说明：

- 行数只统计换行符，不统计分支与状态空间，与认知负荷不相关
- 按行数硬拆会诱导错误拆分（600 行处一刀切，导致共享状态被迫复制、两边不同步）
- 声明型文件（字段定义表）天然长但认知负荷低；逻辑型文件短但可能高危。行数指标会把这两类判反

保留 600 这个阈值，是因为它确有现实成本：**文件越大，按需分段读取时越容易漏上下文、改错地方。** 这是协作成本指标，不是质量指标——所以说的是「超过要解释」，不是「超过就不合格」。

## 七、🟡 测试规范

- `rules` 是纯函数，**必须**分支全覆盖

- `persist` 必须测「旧版本存档能读进来」
- 全量测试必须全绿才算完成，不接受「就一项红的」

## 九、🟡 违规处理

| 次数 | 处理 |
|---|---|
| 第一次 | 当场退回，补齐后重新过第八节全表 |
| 第二次 | 在该模块的架构说明里**记录违规内容与修补方案**，标注这次修补是否属于治标 |

**不强制重写模块。** 重写的成本通常是局部修补的十倍，且不保证结果更好。记录比推倒重来更有价值——它留下的是「这里曾经出过什么问题」的知识。

## 十、🟡 规范自身的修订流程

> 规范不是刻在石头上的。但改规矩必须留痕，否则规矩会越改越松。

### 10.1 允许直接修改条款正文

条款正文**始终保持最新状态**。禁止叠加式追加新旧条款（会导致文档内部自相矛盾：上文写红线，末尾写改成阈值）。

### 10.2 修订必须满足三条

| 要求 | 说明 |
|---|---|
| 写明改了什么 | 具体到条款编号 |
| 写明为什么改 | 触发原因：发现条款不可判定 / 技术错误 / 实际成本过高 |
| 升级版本号 | 主版本 = 红线条目变化；次版本 = 阈值或措辞调整 |

### 10.3 修订记录格式

见文末。每条包含：时间、版本、改了什么、为什么。

### 10.4 禁止的修订

- 🔴 因为「这条执行起来麻烦」而删掉红线 —— 麻烦不等于不合理，要说明具体哪里不成立
- 🔴 在新项目刚起步时放宽红线 —— 起步期最该严，跑起来再松等于没松
- 🔴 不留痕迹的静默修改

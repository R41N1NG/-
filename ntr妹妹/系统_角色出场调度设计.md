## 一、范例卡到底做了什么

先梳理三份规范的实际机制，看清楚边界在哪。

### 1.1 四层解耦模型

| 层 | 职责 | 谁负责 |
|---|---|---|
| 表现与交互层 | 正则渲染、状态栏、开局网关 | Regex 脚本 |
| 状态机与中控层 | 变量池、时钟步进、数值检定、台账同步 | Tavern Helper 脚本 |
| 知识与生态层 | 世界书：总纲 / 场景 / 角色双轨 / 台账 | 世界书（按需激活） |
| 主卡核心层 | Description / First Message / Scenario | 卡元数据 |

### 1.2 数据怎么流动

```
LLM 每轮生成
   ├─ <content>     纯叙事正文
   └─ <status_bar>  结构化申报
        ├─ <time elapsed="30" end="1日08:30" />
        ├─ <move to="4F_Corridor" />
        ├─ <injury level="1" type="scratch" />
        ├─ <focus npc="npc_01" />
        └─ <npc_mind>（对玩家屏蔽，对 LLM 可见）
              ↓
        中控脚本解析申报
              ↓
        apt_mvu 变量池（单一真源）
              ↓
        世界书台账条目 + 状态栏 HUD
              ↓
        注入下一轮提示词
```

### 1.3 角色信息怎么按需激活

角色拆三层，全部走变量宏：

| 变量 | 体积 | 触发方式 |
|---|---|---|
| `char_census_{id}` | ~80 字 | 常驻名单速览 |
| `char_d1_{id}` | 200~300 字 | 世界书条目 A，keys = 角色名 |
| `char_d3_{id}` | 800~1000 字 | 世界书条目 B，keys = 角色名 |

**没有冗余 Token**：名字没出现，条目就不激活，全量人设不进上下文。

## 二、范例卡的空白在哪

三份规范里翻了三遍，**没有一处定义 NPC 如何自主决定自己的行为**。

它的 NPC 是这样运转的：

```
LLM 写到哪里，NPC 就在哪里
LLM 觉得该出现谁，谁就出现
LLM 觉得该做什么，就做什么
```

中控脚本只做三件事：

1. **记账**：把 LLM 申报的事实写进变量池
2. **校验**：算出数值（HP 扣了多少、时间过了多久）
3. **回注**：把台账塞回下一轮提示词

> **一句话：范例卡解决的是「状态不失忆」，没解决「角色自己会动」。**

### 2.1 这带来三个实际问题

| 问题 | 表现 |
|---|---|
| **角色没有时间感** | 玩家不找她，她就永远停在原地，一天和一年没区别 |
| **堕落靠玩家触发** | 玩家不推进，奥萝拉永远在小镇站着，不会自己去领主府 |
| **出场看 LLM 心情** | 该出现的人没出现，不该出现的突然冒出，没有可预期的规律 |

这正是 `系统_角色自主行动设计.md` 要补的第一层。而「条件出场」是第二层。

## 三、两套架构怎么对接（关键）

### 3.1 核心矛盾

| | 范例卡 | 我们的 agency |
|---|---|---|
| 谁来决策 | LLM | 脚本 |
| 状态从哪来 | LLM 申报 | 脚本计算 |
| LLM 的角色 | 决策者 | 表演者 |

**如果直接把脚本算出的状态塞给 LLM，会和 LLM 已经申报的状态打架。**

### 3.2 解法：同源注入

```
        ┌─────────────────────────────┐
        │      apt_mvu 变量池          │
        │   （唯一的真源，谁都不能绕过）│
        └──────────▲──────────────────┘
                   │
        ┌──────────┴──────────┐
        │                     │
   LLM 申报              agency 推演
   （演出来的事实）       （后台跑出来的事实）
        │                     │
        └──────────┬──────────┘
                   ↓
            同一个写入接口
```

**规则：无论事实来自 LLM 还是脚本，都必须走同一个写入接口，写进同一个变量池。**

这样一来：

- LLM 不需要知道自己看到的状态是脚本算的还是自己申报的
- 提示词格式完全不变，世界书条目的变量宏照旧能用
- 冲突时按时间戳裁决，后写的覆盖先写的

### 3.3 对接表

| 范例卡组件 | 我们的系统怎么接 |
|---|---|
| `apt_mvu.npcs[id]` | agency 的 `characters[id]` 直接写这里 |
| `<status_bar>` 申报 | 保留。LLM 申报和脚本推演同时存在，脚本推演结果标记 `source: 'engine'` |
| 世界书角色条目 A/B | 不变。仍是 `{{getvar::char_d1_id}}` |
| 世界书台账层 | **新增一条 `<presence>` 台账**（见第五节） |
| 中控时钟 `total_min` | 与 agency 的「时段」换算：1 时段 = 240 分钟（默认） |
| Regex 管道 | 不需要改。脚本产出仍是文本，走同一条渲染链 |

### 3.4 谁先谁后

```
每个对话回合：
  1. [脚本] 检查是否该推进时段（每 4 回合）
  2. [脚本] 若推进 → agency 跑一轮 → 产出事件 + 新状态
  3. [脚本] 写入 apt_mvu，标记 source: 'engine'
  4. [LLM ] 生成正文，可申报自己的状态变化（source: 'llm'）
  5. [脚本] 解析申报，合并进 apt_mvu
  6. [脚本] 渲染状态栏 + 更新在场台账
```

**关键：脚本先跑，LLM 后演。** 脚本给的是"世界已经发生的事实"，LLM 在此基础上表演，不能推翻。

## 四、条件出场：四道闸门

「条件出场」的本质是回答一个问题：**这一轮，谁该出现在画面里？**

不能靠 LLM 即兴决定，要有一套可判定的规则。

### 4.1 四闸门模型

```
                    ┌─────────────┐
   所有角色 ──────→ │ 闸门1 · 空间 │  同房间/同区域？
                    └──────┬──────┘
                           ↓ 通过
                    ┌─────────────┐
                    │ 闸门2 · 日程 │  这个时段该在哪？
                    └──────┬──────┘
                           ↓ 通过
                    ┌─────────────┐
                    │ 闸门3 · 剧情 │  flags / 门槛满足？
                    └──────┬──────┘
                           ↓ 通过
                    ┌─────────────┐
                    │ 闸门4 · 戏剧 │  优先级排序，限同场人数
                    └──────┬──────┘
                           ↓
                    在场名单（≤3 人）
```

### 4.2 闸门详解

#### 闸门 1 · 空间（物理）

```js
npc.location === player.location
```

**这是硬条件**，不满足绝对不出场。除非有「远程事件」（传讯、看见、听见）。

**位置不是手填的**，由 agency 的「移动」行动决定。角色自己会走动，所以位置会变。

#### 闸门 2 · 日程（时间）

每个角色有作息表：

```js
schedule: {
  'morning':  ['church', 'town'],
  'afternoon':['manor', 'town'],
  'night':    ['manor'],           // 夜晚只在领主府
  'deep_night':[ 'manor']
}
```

角色只有在日程允许的地点才可能被判定为「在那儿」。

> 日程不是硬锁——`corruption` 高时，角色可能违反日程（深夜偷偷溜出去）。这由 agency 的移动行动自动产生，不需要额外写规则。

#### 闸门 3 · 剧情（逻辑）

```js
requires: {
  flags: { lord_offered_job: true },   // 剧情标记
  corruption: '>=30',                  // 堕落度门槛
  time: { phase: 'night' },            // 时段限制
  notFlags: { eileen_expelled: true }  // 反向条件
}
```

#### 闸门 4 · 戏剧（舞台）

同一场景塞太多人，画面会糊。所以：

```js
maxOnStage: 3              // 同场最多 3 人
priority: 'screen_time'    // 按"多久没出场"排序，久未露面的优先
```

**为什么要限人数**：LLM 的注意力是有限的。三个角色同时在场，文笔质量会明显下降；只留一个人，反而能写透。

### 4.3 三种出场模式

| 模式 | 触发逻辑 | 适用 | 例子 |
|---|---|---|---|
| **日程式**（被动） | 角色自己按schedule待在某地，玩家走过去就遇上 | 日常、偶遇 | 奥萝拉白天在教堂 |
| **触发式**（事件） | 满足 flag 才出现，出现即意味着某事发生 | 剧情节点 | 玩家进赌场 → 妮丝正在里面输钱 |
| **追猎式**（主动） | 角色**主动来找玩家**，由 agency 决定 | 高张力 | 艾琳察觉不对，深夜来找伯里 |

**追猎式是三种里最有戏的**，但也是最容易失控的——如果每个角色都主动找玩家，玩家会被淹没。所以要加冷却：

```js
pursuitCooldown: 8   // 追猎过后至少 8 个时段不再主动找
```

### 4.4 反向：怎么「保证不出场」

这往往比「保证出场」更重要。

```js
absent: {
  flags: { eileen_left_town: true },     // 已经离镇
  until: { day: 5 },                     // 第 5 天才回来
  reason: 'guarded'                      // 闭关/被囚禁/重伤
}
```

**`absent` 优先级最高**，压过其他一切条件。用来防止「人都被抓走了还在街上晃」这种逻辑崩坏。

## 五、在场台账（给 LLM 看的）

### 5.1 新增台账条目

在范例句的「动态台账层」里加一条 `<presence>`，`constant: true`：

```xml
<presence>
在场：奥萝拉（女仆装·手上有酒渍·低头不语）｜距离：近
     妮丝（门口·正在张望·手里攥着筹码）｜距离：中
缺席：古兰（在旅店二楼）、伊丝娜（酒馆）
</presence>
```

### 5.2 信息分层

**关键：只写「能看到什么」，不写「为什么」。**

| 层 | 写什么 | 例子 |
|---|---|---|
| ✅ 客观可见 | 外貌、位置、动作、可见痕迹 | `裙摆有酒渍` |
| ❌ 内在状态 | 心理、动机、隐情 | `她刚被侵犯过` |
| ❌ 未发生的事 | 猜测性信息 | `她今晚还会去` |

> 这条纪律和范例卡的 `<npc_mind>` 分工一致：**`<npc_mind>` 给 LLM 看内心，`<presence>` 给玩家看外在**。
> 但 `<presence>` 是台账（常驻），`<npc_mind>` 是申报（每轮）。两者不重叠。

### 5.3 为什么不用 `<focus npc="...">`

范例卡已经有 `<focus>>`，但它是 **LLM 申报「我这轮聚焦谁」**，是结果不是原因。

`<presence>` 是**脚本算出来的在场名单**，是原因。两者的差别：

```
脚本算：这些人此刻在这个房间（客观）
LLM 选：这轮我写其中哪一个（主观）
```

脚本给名单，LLM 挑重点。**这样既保证逻辑自洽，又保留叙事自由。**

## 六、数据结构

### 6.1 角色增加出场字段

```js
{
  id: 'aurora',
  // ……原有字段……
  location: 'manor',              // 由 agency 的移动行动更新
  schedule: {                     // 日程白名单
    morning:   ['church', 'town'],
    afternoon: ['manor', 'town'],
    night:     ['manor'],
    deep_night:['manor']
  },
  presence: {                     // 出场控制
    mode: 'schedule',             // schedule | trigger | pursuit
    requires: {},                 // 剧情条件
    absent: null,                 // 缺席规则（优先级最高）
    priority: 1,                  // 戏剧优先级（越大越优先）
    lastSeenAt: 0,                // 上次出场时段，用于轮换
    pursuitCooldown: 0            // 追猎冷却剩余
  }
}
```

### 6.2 出场判定结果

```js
{
  day: 3,
  phase: 'night',
  location: 'manor',
  present: [
    { id: 'aurora', distance: 'near', cues: ['女仆装', '裙摆有酒渍', '低头不语'] },
    { id: 'nise',   distance: 'mid',  cues: ['门口', '正在张望', '攥着筹码'] }
  ],
  absent: [
    { id: 'gulan',  where: '旅店二楼' },
    { id: 'isna',   where: '酒馆' }
  ],
  offStage: ['eileen']            // 因人数限制被挤出
}
```

## 七、和 agency 系统的具体衔接

### 7.1 移动也是行动

角色换地方，不是脚本硬搬，而是 agency 选出来的：

```js
{
  id: 'aurora_go_manor',
  label: '去领主府',
  base: 20,
  requires: { drives: { need: '>55' } },
  effects: { location: 'manor', drives: { need: -5 }, corruption: +1 },
  blockedBy: []
}
```

**这样位置变化是"角色的决定"，不是"系统的安排"。** 玩家看到的是"她自己去的"，不是"被传送到那儿"。

### 7.2 时段推进后的完整流程

```
sm_turn.tick()
  ├─ 1. 时间 +1 时段
  ├─ 2. agency：每个角色选一个行动（可能是移动）
  ├─ 3. 更新所有 character.location
  ├─ 4. presence：跑四闸门，算出 present / absent / offStage
  ├─ 5. observe：按玩家位置过滤事件可见性
  └─ 6. emit：产出 <presence> 台账 + 世界快照
```

### 7.3 新增模块

在原有八个模块基础上增加一个：

| 模块 | 职责 | 依赖 |
|---|---|---|
| `sm_presence` | 出场判定：四闸门、人数限制、缺席规则 | core, schema, rules |

层级放在 `sm_rules` 之后、`sm_effect` 之前：

```
L2  sm_rules
      ↓
L3  sm_agency   sm_presence   sm_observe
```

> **为什么单独一个模块**：出场判定既有纯逻辑（条件判断），又有排序（priority），还有状态（cooldown）。塞进 `rules` 会让纯函数不纯，塞进 `effect` 会让结算器管调度。

## 八、验证要点

实现后必须验证这五条：

| # | 验证项 | 期望 |

| 4 | 同场人数从不超过 3 | 闸门 4 生效 |
| 5 | 被标记 absent 的角色绝不出现 | 缺席规则优先级最高 |

## 九、设计取舍

| 决定 | 理由 | 放弃的方案 |
|---|---|---|
| 同源注入（脚本与 LLM 走同一写入口） | 避免两套状态打架，且提示词格式零改动 | 脚本另建一套变量（会和 LLM 申报冲突） |
| 位置由行动决定，不硬搬 | 玩家感知到的是"她自己去的" | 脚本直接设置 location（像传送） |
| 四闸门串联，不是加权分 | 出场是布尔判断，不是程度问题 | 打分制（会让不该出现的人有概率出现） |
| 限同场 3 人 | LLM 注意力有限，人多则文笔崩 | 不限（画面糊、焦点散） |
| `<presence>` 只写可见信息 | 和 `<npc_mind>` 分工，防信息泄漏 | 直接写心理（破坏迷雾） |
| 保留 `<focus>` | LLM 的叙事自由要留着 | 脚本强制指定焦点（僵化） |

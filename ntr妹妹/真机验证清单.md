# 真机验证清单 · 四条链路

> **定稿时间**：2026-11-10 07:52 (UTC+8)
> **编写时版本**：核心 v2.1.0。当前导入与脚本入口见[角色卡说明](奥森德/最新角色卡/README.md)。
> **前置**：所有验证在**测试聊天**里做，先用一条新聊天，不要拿主存档试。
> **原则**：四条链路互相独立，一条通过不能推出另一条通过。判定只看证据，不看"没报错"。

---

## 〇、为什么必须分开验

| 链路 | 它回答的问题 | 失败的后果 | 靠什么证伪 |
|---|---|---|---|
| 一 · 存储持久化 | 数据写下去了吗，刷新还在吗 | 每轮重来，状态全丢 | 刷新后读 `timeMin` |
| 二 · 宏作用域 | 世界书 `{{getvar::}}` 读得到系统写的变量吗 | 世界书条目空白，AI 什么都不知道 | 探针条目 + 看实际提示词 |
| 三 · 生成入口 | 生成前注入到了吗，回复后队列确认了吗 | AI 看不到待演绎，队列永远不消费 | 提示词里搜台账锚点 + 队列前后对比 |
| 四 · 角色切片导出 | `char_d1/d3` 从哪来 | 角色档案空白或数值泄漏进叙事 | 代码审查 + 条目文本 |

链路一的 `mode` 只说明**走哪条驱动分支**，不说明写入生效；链路二的探针通过也不说明注入到位。三者串联才算接通。

## 一、链路一 · 存储持久化

### 步骤

在酒馆控制台（F12）执行：

```js
await OKH_APP.init();
console.log('[L1] info', OKH_APP.info());
const before = OKH_APP.world()?.timeMin;
console.log('[L1] 推进前 timeMin =', before);
const r = await OKH_APP.step(30);
console.log('[L1] step 结果', {
  advanced: r?.advanced, duplicate: r?.duplicate,
  from: r?.from, to: r?.to, published: r?.published
});
console.log('[L1] 存档键 =', OKH_APP.W.session().key, '| revision =', OKH_APP.info().revision);
```

**不要在这一步调 `start()`**——它会 `attach()` 事件钩子 + 起 HUD（[okh_app_entry.js:30-36](奥森德/src/app/okh_app_entry.js#L30-L36)），把链路三的变量混进来。

然后**刷新页面**（整页 F5，不是切聊天），重新执行：

```js
console.log('[L1] 刷新后', {
  chatId: OKH_APP.info().chatId,
  revision: OKH_APP.info().revision,
  timeMin: OKH_APP.world()?.timeMin,
  day: OKH_APP.world() ? Math.floor(OKH_APP.world().timeMin / 1440) + 1 : null,
  minOfDay: OKH_APP.world()?.timeMin % 1440
});
```

### 判定

| 证据 | 结论 |
|---|---|
| 刷新后 `timeMin` 与刷新前一致，`revision` 不回退 | ✅ 落盘成立 |
| 刷新后 `timeMin` 回到 0 或 `world` 为 null | ❌ 写入未落到该聊天变量，或 key 归属错 |
| 刷新后 `revision` 变小 / 存档报"版本或聊天归属不匹配" | ❌ chatId 不稳定（换模型/换分支会变） |
| `step` 抛 "存储接口报告写入失败" / "回读不一致" | ❌ 驱动层问题，链路二不用做了，先解决这个 |

`info().mode` 预期是 `helper-chat`（宿主有 `getVariables/replaceVariables`）或 `getvar`（只有 `getvar/setvar`）。两个都可用，**但写的是不同作用域的东西**，正是链路二要查的。

## 二、链路二 · 宏作用域（关键分叉）

链路一通过只说明"走 `chat` 类型变量存进去了"。世界书宏 `{{getvar::x}}` 读的是哪一层，是独立问题。

### 步骤 2.1 · 用系统自己的驱动发布探针

不要用未经确认作用域的 `setvar`/`getvar` 手动写，那会绕开回读校验。走 `publishDerived`：

```js
const s = OKH_APP.W.session();
const rev = OKH_APP.world().bg.revision;
try {
  await OKH_APP.W.publishDerived(s, {
    'okh.probe': 'probe_20261110',     // 带点前缀
    'probe': 'probe_nodot'             // 不带点
  }, rev);
  console.log('[L2] 写入并回读通过', { key: s.key, revision: rev });
} catch (e) {
  console.warn('[L2] 写入或回读失败：', e.message);
}
```

`publishDerived` 内部会做 `rawGet(s, key) === value` 回读校验（[okh_app_world.js:143-148](奥森德/src/app/okh_app_world.js#L143-L148)）。**它抛错本身就是有效证据**：说明写入是异步的、被宿主吞掉、或 `replaceVariables` 没落到可读位置。

### 步骤 2.2 · 临时世界书条目（探针，验完即删）

新建一条世界书条目：

| 项 | 值 |
|---|---|
| 名称 | `ZZ_探针_作用域` |
| 触发 | 常驻 constant |
| 位置 | `at_depth`，深度 0（最近的深度，保证进上下文） |
| 内容 | 见下 |

```text
[探针A带点]{{getvar::okh.probe}}
[探针B系统台账]{{getvar::okh_gpt.ledger}}
[探针C无点]{{getvar::probe}}
[探针D旧口径]{{getvar::okh.ledger}}
```

探针 B 直接用系统**正在写**的 key（[okh_app_hook.js:67](奥森德/src/app/okh_app_hook.js#L67)），不需要额外写入；探针 D 用旧说明文档的口径。四条一次把三件事分开。

### 步骤 2.3 · 看实际提示词

发一句无意义的话（如"继续"），打开**提示词查看器 / Prompt Viewer**，在请求体里搜 `[探针A`，读回填结果。

### 判定矩阵

| A 带点 | B 系统台账 | C 无点 | D 旧口径 | 结论 | 下一步 |
|---|---|---|---|---|---|
| 有值 | 有值 | 有值 | 空 | 宏作用域 = 系统写入作用域，带点也能解析 | ✅ 直接进链路三；问题纯粹是"系统没写 char_d1" |
| 有值 | 有值 | 空 | 空 | 带点可解析，无点不行 | 罕见，说明该宿主把点当命名空间；变量名必须带前缀 |
| 空 | 空 | 空 | 空 | **宏读的不是 chat 作用域** | ⛔ 换方案：改走 `setExtensionPrompt` 注入口，或改 world 驱动为 global 作用域 |
| 空 | 空 | 有值 | 空 | 只认无点短名 | 变量名全部去前缀 |
| 空 | 有值 | — | — | 逻辑上不成立，若出现说明探针 A 写入失败但 B 成功 | 回看步骤 2.1 的报错 |

**这张表是本次验证的核心产出。** 它决定第 4 步是"加一层导出"还是"换整条注入方案"。

> ⚠️ 探针条目验完立刻删除。它的内容是给 AI 读的，留着会污染叙事。

## 三、链路三 · 生成入口

启动没报错只能证明接口探测与注册通过（[okh_app_hook.js:215-238](奥森德/src/app/okh_app_hook.js#L215-L238)），不证明注入到位。

### 步骤 3.1 · 取锚点

```js
const r = await OKH_APP.start();
console.log('[L3] start', { hooked: r.hooked, hud: r.hud, storage: r.storage });
const lg = OKH_APP.ledger();            // 打印台账全文并返回
const anchor = (lg || '').split('\n')[0];
console.log('[L3] 提示词锚点 =', JSON.stringify(anchor));
console.log('[L3] 回复前队列', OKH_APP.queue().filter(e => e.status === 'pending').length);
```

`ledger()` 返回的就是 `A.buildLedger(world)` 的原文（[okh_app_debug.js:66-72](奥森德/src/app/okh_app_debug.js#L66-L72)），生成前注入拼的就是这段（[okh_app_hook.js:168](奥森德/src/app/okh_app_hook.js#L168)）。

### 步骤 3.2 · 生成一轮后核对

发一句话，等回复完整落地，再执行：

```js
const rep = OKH_APP.H.lastReport();
console.log('[L3] 回复后', {
  advanced: rep?.advanced, duplicate: rep?.duplicate,
  pending数: rep?.pending, published: rep?.published,
  from: rep?.from, to: rep?.to
});
console.log('[L3] 队列', OKH_APP.queue().filter(e => e.status === 'pending').length);
console.log('[L3] 残留提示词', OKH_APP.H.lastReport()?.published);
```

### 判定

| 检查点 | 通过 | 不通过的含义 |
|---|---|---|
| 提示词查看器里搜得到 `anchor` 原文 | 生成前注入成立 | 注入没到位，或注入了但被别的扩展覆盖 |
| `advanced === true` 且 `from→to` 前进 | 回复后确认队列成立 | 事件没触发 / `MESSAGE_RECEIVED` 未绑定 |
| 队列 `pending` 数下降或条目状态变更 | 待演绎被消费 | 消费逻辑没接上，下一轮会重复注入 |
| `published === false` | ⚠️ 权威状态已提交，但派生缓存没发布 | 见下方表述修正 |

### 关于"派生失败"的准确表述

`publish()` 失败时**有控制台警告**（`console.warn('[APP] 权威状态已保存，派生缓存发布失败：', ...)`），**并返回 `published:false`**，但**不会撤销已经成功提交的世界状态**（[okh_app_hook.js:71-72](奥森德/src/app/okh_app_hook.js#L71-L72)、[okh_app_hook.js:129-132](奥森德/src/app/okh_app_hook.js#L129-L132)）。

所以：
- ❌ 不是"静默失败"
- ✅ 是"权威状态已提交、派生缓存降级"——数据没丢，只是 AI 这一轮看不到
- ✅ 处理方式：**增强诊断显示，不重新结算同一轮**。重跑 `step` 会因 `receipts` 幂等判重（[okh_app_hook.js:103-109](奥森德/src/app/okh_app_hook.js#L103-L109)），要么被拒 `duplicate`，要么触发 restore，都不该用在这里。正确做法是补一次 `OKH_APP.H.publish(OKH_APP.W.session())` 单独重发派生缓存。

## 四、链路四 · 角色切片导出（三条链路通过后才动）

### 4.1 现状（代码证据）

`publish()` 只发布 5 个 key，没有任何 `char_d1_*` / `char_d3_*`：

```js
// okh_app_hook.js:64-70
'okh_gpt.pendingText', 'okh_gpt.pendingIds',
'okh_gpt.ledger', 'okh_gpt.watch', 'okh_gpt.derivedRevision'
```

`publishDerived` 的注释自己写着「仅为旧世界书兼容缓存」（[okh_app_world.js:142](奥森德/src/app/okh_app_world.js#L142)）——它就是为这类导出预留的入口，加导出**不需要动存档内核**。

### 4.2 设计约束

| 切片 | 内容 | 来源 | 是否落变量 |
|---|---|---|---|
| `char_census` | 80 字速览 | 静态档案 | ❌ 常量文本即可 |
| `char_d1_{id}` | 心智指南 + 【近期状态】 | 静态 base + 动态翻译 | ✅ 需落变量 |
| `char_d3_{id}` | 800~1000 字全案档案 | **纯静态档案原文** | ❌ **不落变量** |

`char_d3` 是静态的：它不随时间、位置、数值变化。**把它写成世界书条目的常量文本，比每轮写一遍变量更省**——省一次写盘、省一次回读校验、少一个可能对不上的 key。这符合「系统做减法」。

`char_d1` 必须落变量，因为尾部要挂【近期状态】。静态 base 从 `设定_世界书正式条目与角色切片全案.md` 各角色「心智涌现指南」段抽取，动态段由数值翻译生成（旧版 `MATRIX` / `describe()` 的思路，见 [缺口清单.md:33](缺口清单.md#L33)）。**数值不进文本**：`corruption: 35` 不能出现在 `char_d1` 里，要翻成叙事描述。

### 4.3 实施位点

```js
// okh_app_hook.js:64-70 的 values 里追加，与 okh_gpt.* 同一批发布
for (const npc of Object.values(world.npcs)) {
  values['okh_gpt.char_d1_' + npc.id] = renderCharD1(world, npc);
}
```

- 新增独立模块负责 `renderCharD1`（职责：切片翻译器），`publish()` 只调用，不含拼装逻辑——符合规范 2.1「一文件一职责」
- 不新增第二次写盘：跟随 `publishDerived` 同批提交
- 不做全文盲目替换：按 4.x 确定的 key 清单逐条改世界书条目，改完用 grep 复核零残留

## 五、前置冲突（必须在第 4 步之前定案）

### 5.1 变量名三套口径并存

| 口径 | 出现位置 | 与当前系统是否一致 |
|---|---|---|
| `okh_gpt.ledger`（下划线） | 系统实际写入 [okh_app_hook.js:67](奥森德/src/app/okh_app_hook.js#L67) | ✅ 真源 |
| `okh.ledger` / `okh.char_d1_xxx`（点） | [世界书配置说明.md:38,68,111-115](世界书配置说明.md#L38) | ❌ 旧版口径 |
| `char_d1_gulan`（无前缀） | [世界书条目/03_小队全员档案.md:79](世界书条目/03_小队全员档案.md#L79) 等全部条目正文 | ❌ 无前缀 |

**注意**：这不只是 `char_d1` 缺失问题——连「当前局势」条目写的 `{{getvar::okh.ledger}}` 也对不上系统的 `okh_gpt.ledger`。也就是说**那条最重要的常驻条目现在也是空的**。

### 5.2 `世界书配置说明.md` 整份是 legacy 口径

第 126-152 行的验证步骤调 `__OKH__.modules.turn.runTurn()` 与 `__OKH__.modules.core.read()`——那是 12 脚本自研版的 API，在 v2.1.0 里已不存在（现在是 `OKH_APP.*`）。这份文档要么重写，要么标 `@status legacy`。

### 5.3 建议

统一到 `okh_gpt.` 一个家族：`okh_gpt.char_d1_{id}`。理由：系统已整体使用该前缀，再引入 `okh.` 会形成第三套命名族，违反真源唯一律。世界书条目文本随之逐条改，不做全文替换。

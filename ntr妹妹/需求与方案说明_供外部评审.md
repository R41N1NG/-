# 角色自主行动系统 · 需求与方案说明

> **用途**：给外部评审用。本文件独立可读，不依赖其他文档。
> **日期**：2026-11-09
> **环境**：SillyTavern（酒馆）+ Tavern Helper（酒馆助手）浏览器脚本

---

## 第一部分 · 需求

### 1.1 用户的原始需求

> 「在后台脚本控制每个角色的自主行动，或者说是让角色们按照预设的行为自主发展」

> 「不要锁定某一个人，我们要完成的是针对所有人的系统」

> 「让这套系统『动起来』，每隔一定固定时间，角色会按照我们预设的行为进行行动，当满足某些条件时，就会触发『事件』」

> 「（监听数据）AI 看不到」

### 1.2 需求拆解

| # | 需求 | 说明 |
|---|---|---|
| R1 | **角色自主行动** | NPC 不依赖玩家触发，自己决定做什么、去哪里 |
| R2 | **按预设行为** | 行为受角色人设约束，不能 OOC |
| R3 | **自主发展** | 状态随时间演变（如堕落度、关系），不是静态的 |
| R4 | **通用系统** | 逻辑代码不能绑定具体角色名，加角色只改配置 |
| R5 | **定时推进** | 每隔固定条件，世界必然向前走一步（不依赖 AI 配合） |
| R6 | **条件事件** | 满足特定条件时触发事件，改变世界状态 |
| R7 | **隐藏监听** | 能观测所有角色的位置与状态，但不暴露给 AI 和玩家 |

### 1.3 项目背景（最小必要）

这是一个西幻题材的文字角色卡项目，包含：

- 玩家角色 1 名（不参与推演）
- 女性 NPC 5 名（各有堕落线）
- 反派势力若干

核心玩法是「NTR 叙事」：NPC 在玩家不干预的情况下，会因各自的处境（缺钱、好奇、责任感）逐步走向失控。

**系统的目的不是替玩家写故事，而是让世界在玩家背后真实地运转。**

## 第二部分 · 硬约束

### 2.1 宿主环境的限制

SillyTavern 脚本运行在浏览器里：

| 能做 | 不能做 |
|---|---|
| 读写变量池（`getvar`/`setvar`） | 操作文件系统 |
| 挂钩消息事件 | 常驻后台定时器（页面关了就停） |
| 修改 DOM | 主动调用 LLM |
| 持久化到聊天元数据 | 使用 ES module 的 `import` |

**关键约束：没有真正的「后台」。** 只能在「用户发消息」「AI 回复」这些事件上挂钩子。

所以系统的实现方式是：

```
每轮对话 → 钩子触发 → 检查是否该推进 → 该推进就推演一次
```

**推演是离散的，不是连续的。**

### 2.2 架构契约（不可违反）

项目已有一套成熟架构规范（下称「范例卡」），系统必须服从它，不得新增契约：

| 约束 | 具体内容 |
|---|---|
| **不新增 XML 标签** | 状态栏的标签集是封闭的（`<time>` `<move>` `<injury>` `<focus>` `<npc_mind>` 等），一个不加 |
| **不新增世界书条目类型** | 四池固定：静态总纲 / 场景空间 / 角色双轨 / 动态台账 |
| **不改 HUD 布局** | 只能填已有字段 |
| **单一真源** | 所有状态只存一份，不许出现第二份副本 |

### 2.3 范例卡的既有机制

| 机制 | 说明 |
|---|---|
| 双层闭合 | `<content>`（正文）+ `<status_bar>`（结构化申报，每轮一个） |
| 变量池 | `apt_mvu` 命名空间，中控脚本读写，LLM 不直接碰 |
| 世界书变量宏 | `{{getvar::char_d1_xxx}}`，把变量注入提示词 |
| 角色三层切片 | `char_census`（80字）/ `char_d1`（心智，200-300字）/ `char_d3`（全案，800-1000字） |
| 内外分离 | `<npc_mind>` 对玩家屏蔽，对 LLM 可见 |

### 2.4 代码规范（项目自定）

| 条款 | 要求 |
|---|---|
| 分模块 | 一文件一职责，单文件超 600 行触发复核 |
| 依赖单向 | 图层化，禁止反向与循环依赖 |
| 注释 | 四个必填字段：`@module` `@updated` `@status` `@reason` |
| 数据与逻辑分离 | 逻辑代码不许出现角色名 |

## 第三部分 · 当前方案

### 3.1 模块划分（12 个脚本，按加载顺序）

| # | 文件 | 职责 | 行数 | 依赖 |
|---|---|---|---|---|
| 0 | `okh_boot` | 全局注册表 + 钩子表 | 34 | 无 |
| 1 | `okh_core` | 变量读写唯一入口（含存储适配层） | 142 | boot |
| 2 | `okh_schema` | 数据结构 / 地点表 / 时段表 / 阶段阈值 | 264 | core |
| 3 | `okh_rules` | 纯函数判定（可用行动、底线、前置条件） | 203 | core, schema |
| 4 | `okh_agency` | 效用打分 + 加权随机决策 | 205 | core, schema, rules |
| 5 | `okh_presence` | 出场四闸门 | 140 | core, schema, rules |
| 6 | `okh_translate` | 数值 → 描述性文本 | 131 | core, schema |
| 7 | `okh_turn` | 时间步进 + 主循环 + 事件钩子 + 节奏控制 | ~490 | 除 hud/debug 外全部 |
| 8 | `okh_hud` | 在场与监听渲染 | 110 | boot（订阅钩子） |
| 9 | `okh_debug` | 调试工具 | 235 | 全部 |
| 10 | `okh_data` | **数据层（唯一写角色名的地方）** | ~360 | core, schema |
| 11 | `okh_event` | 条件事件系统 | 215 | core, schema, rules |

**依赖方向**：

```
boot(0) → core(1) → schema(2) → rules(3) → agency/presence/translate/event(4) → turn(5) → hud/debug(6)
                                      ↑
                                    data(2，与 schema 同层)
```

`turn` 不直接调用 `hud`，通过钩子表 `hooks.afterTurn` 通知。

### 3.2 核心算法

#### 决策：效用打分 + 加权随机

```
score = base × 标签修正 × 惯性 × 闲置补偿 × 噪声

base      行动本身的吸引力（配置）
标签修正   按行动 tags 与角色 drives 匹配，查规则表
惯性      1 + 0.25 × min(做过次数, 4)        ← 做过的事更容易再做
闲置补偿   1 + 0.15 × min(闲置轮数, 6)        ← 久不做的事更有吸引力
噪声      0.8 ~ 1.2（可复现种子）
```

**不取最高分，而是按分数占比加权随机。**

理由：取最高分会让角色变成可预测的机器，同样状态下永远做同一件事。

#### 标签修正规则表（配置驱动）

```js
{ tag: 'money',     drive: 'need',      op: '>', val: 60, mult: 1.40 }
{ tag: 'expose',    drive: 'shame',     op: '>', val: 60, mult: 0.75 }
{ tag: 'risk',      drive: 'curiosity', op: '>', val: 60, mult: 1.35 }
{ tag: 'risk',      drive: 'fear',      op: '>', val: 65, mult: 0.70 }
{ tag: 'duty',      drive: 'duty',      op: '>', val: 65, mult: 1.25 }
{ tag: 'bond',      drive: 'loyalty',   op: '>', val: 65, mult: 1.25 }
{ tag: 'humiliate', drive: 'pride',     op: '>', val: 70, mult: 0.60 }
{ tag: 'risk',      drive: null,        op: 'sanity<', val: 40, mult: 1.20 }
```

加规则 = 加一行数据，不动代码。

#### 底线机制（防 OOC 的最后一道闸门）

每个角色有一组底线，按**类型**封锁行动：

```js
// 行动声明自己被哪类底线封
action.blockedBy = ['no_physical_contact']

// 角色声明自己有什么底线，以及何时失效
npc.lines = [
  { id: 'no_contact', type: 'no_physical_contact', holdsWhile: { corruption: '<30' } },
  { id: 'keep_orphans', type: 'never_abandon', holdsWhile: { corruption: '<999' } }
]
```

- 匹配的是 `type` 不是 `id` → 角色配置自由，封锁规则统一
- 底线有效时，被封锁行动的权重**直接归零**（不是降权）
- `holdsWhile: { corruption: '<999' }` 表示永不解除（人设锚点）

#### 出场：四闸门串联

```
闸门0 缺席规则（被软禁/离镇）—— 优先级最高，压过一切
闸门1 空间：npc.location === player.location
闸门2 日程：该时段是否允许在这个地点
闸门3 剧情：flags / corruption 门槛
闸门4 戏剧：按 priority 排序，限同场 3 人
```

#### 数值翻译（关键设计）

**AI 永远看不到数字。**

```js
corruption = 35
    ↓ 翻译（4 区间 × 9 驱动力 = 36 条通用模板）
"她开始找理由晚归，说辞一次比一次顺。"
    ↓ 写进变量 okh.char_d1_aurora
    ↓ 世界书 {{getvar::okh.char_d1_aurora}} 注入
AI 看到的：描述，不是数字
```

理由：AI 看到数字会「演数字」，写出「她的堕落度提升了」这种话，人味全没。

#### 定时推进（两套机制并存）

```js
const RHYTHM = {
  everyMessages: 3,      // 每 3 条 AI 消息强制推进一次
  minutesPerTick: 60,    // 每次推进 60 游戏分钟
  useAITime: true        // AI 报了 <time> 就优先用
}
```

```
收到 AI 消息
  ├─ AI 报了 <time elapsed="N"> 且跨时段 → 立即推演
  └─ 否则累计，够 3 条 → 强制推演
```

**保证 AI 不配合时世界也在动。**

#### 事件系统

```js
{
  id: 'evt_id',
  once: true,
  narration: '写进台账的一句话，AI 能看到',
  trigger: {
    dayMin: 5,                          // 第 5 天起
    phase: ['morning'],                 // 时段
    flags: { some_flag: true },         // 世界标记
    anyNpc: { corruption: '>=30' },     // 任一角色满足
    chance: 0.6                         // 概率
  },
  effects: {
    target: 'npc_id' | ['a','b'] | 'all' | null,
    drives: { fear: 15 },
    corruption: 5,
    move: 'location_key',
    setFlags: { result_flag: true }
  }
}
```

事件在**角色行动之前**触发，可影响本轮选择。

### 3.3 数据流

```
AI 回复（含 <time elapsed>）
      ↓
parseElapsed → 累加 sys.total_min → 推导 phase
      ↓ 跨时段 或 够 N 条
runTurn()
  ├─ ① 检查世界事件 → 触发 → 改角色状态 → 写 flags
  ├─ ② 每个角色：agency.decide → applyAction → 漂移 → 翻译
  ├─ ③ presence.resolve → 在场名单
  ├─ ④ 写回变量池
  ├─ ⑤ 通知钩子 → hud 渲染
  ├─ ⑥ 生成 ledger（给 AI 的世界快照）
  └─ ⑦ 生成 watch（隐藏监听，不给 AI）
      ↓
下一轮 AI 生成时世界书读到新状态
```

### 3.4 变量命名

不使用范例卡的 `apt_mvu`（那是另一个项目的命名空间），本项目用 `okh_*` 前缀：

```
okh.sys.total_min      绝对分钟
okh.sys.phase          时段
okh.npcs               全部角色状态
okh.actionLibrary      行动定义
okh.eventLibrary       事件定义
okh.char_d1_{id}       角色心智（世界书读这个）
okh.ledger             世界快照（世界书读这个）
okh.watch              隐藏监听（不进提示词）
```

## 第五部分 · 已知问题与争议点

### 5.1 我不确定的地方

| # | 问题 | 我的倾向 | 需要判断 |
|---|---|---|---|
| 1 | **行动叙述全局共用** | 应该支持个体覆盖 | 奥萝拉「去侍奉」和塞西莉亚「去侍奉」，场景完全不同，但 AI 看到的描述一样 |
| 2 | **翻译文案 36 条够不够** | 够用，但文风需校 | 会不会所有角色读起来像同一个人 |
| 3 | **加权随机 vs 取最高分** | 加权随机 | 取最高分可预测性太强，但加权随机会不会让"该发生的没发生" |
| 4 | **四闸门串联是否过严** | 合理 | 会不会出现"所有人都被挡住，场面空无一人" |
| 5 | **事件在行动之前触发** | 合理 | 还是应该之后触发（事后反应） |
| 6 | **惯性 + 闲置双修正** | 必要 | 早期版本只有惯性，实测会卡在单一行为循环 |
| 7 | **`monitored` 字段默认 true** | 合理 | 新加角色会默认被监听，可能不是本意 |

### 5.2 已经踩过的坑（供参考）

| 坑 | 现象 | 根因 |
|---|---|---|
| 死锁 | 角色永远不堕落 | 底线封住了唯一能提升堕落度的行动，而要解锁底线又必须提升堕落度 |
| 驱动力枯竭 | 角色行为单一 | 一次性资源（如好奇）用完就没动机了，需每轮向基线回归 |
| 行为锁死 | 反复做同一件事 | 惯性只增不减，需配闲置补偿 |
| 静默失效 | 系统装好但不动 | 加载时解构依赖，脚本顺序错时拿到 undefined 不报错 |
| 事件不触发 | 条件看似满足却不发生 | `undefined !== null` 为真，导致误入判断分支 |

### 5.3 设计取舍记录

| 决定 | 理由 | 放弃的方案 |
|---|---|---|
| 不新增 XML 标签 | 用户明确要求服从范例卡 | 自建 `<presence>` 台账 |
| 数值不进提示词 | 防 AI「演数字」 | 直接注入 corruption 数值 |
| 逻辑层零角色名 | 「针对所有人」是硬需求 | 每角色专用模块 |
| 行动用标签而非角色绑定 | 同一行动不同人用出不同味道 | `aurora_work_shift` 这类专属命名 |
| 底线归零而非降权 | 降权仍可能越线 | 权重 ×0.1 |
| 判定与结算分离 | 规则可单独测 | 一个函数搞定 |

## 第六部分 · 希望评审什么

### 6.1 架构层面

1. **12 个模块的划分是否合理？** 有没有职责重叠或遗漏？
2. **`turn` 模块 490 行是否过重？** 它承担了时间步进、主循环、钩子挂载、台账生成、监听快照六件事。
3. **依赖方向是否正确？** `event` 依赖 `rules`，`turn` 依赖 `event`，这个链路合理吗？

### 6.2 算法层面

1. **效用打分公式**：五个乘数（base / 标签 / 惯性 / 闲置 / 噪声）是否过拟合？有没有更简洁的模型？
2. **加权随机**：是否会导致"关键剧情节点永远不触发"？要不要加"保底机制"？
3. **四闸门**：串联是否比加权更合适？

### 6.3 系统层面

1. **这套系统能真正"动起来"吗？** 还是会在实际使用中退化成"随机做点事"？
2. **角色的堕落曲线可控吗？** 会不会要么太快要么太慢，调不到合适？
3. **事件的触发时机**：现在在角色行动之前，是否合理？

### 6.4 缺失的部分

以下是我意识到但还没做的：

- 角色之间的**相互影响**（A 的行为会不会改变 B 的状态？）
- **玩家行为的反馈**（玩家做了什么，会不会影响角色的驱动力？）
- **存档迁移**（版本升级后旧数据怎么办）
- **多角色复用同一行动的叙述区分**

## 附录：一次完整回合的伪代码

```js
onMessageReceived() {
  const text = 最后一条 AI 消息
  
  // ① 时间
  const elapsed = parseElapsed(text)        // 从 <time elapsed="30"> 抠出 30
  if (elapsed) total_min += elapsed
  _msgCount++
  
  const phaseChanged = (新阶段 !== 旧阶段)
  const rhythmDue = (_msgCount >= 3)
  
  if (!phaseChanged && !rhythmDue) return
  
  // ② 推演
  const npcs = read('npcs')
  const flags = read('world.flags')
  
  // 2.1 世界事件
  for (const ev of event.checkAll({ day, phase, flags }, npcs)) {
    event.apply(ev, npcs, { flags })       // 改驱动、改堕落、写标记
  }
  
  // 2.2 角色行动
  for (const npc of npcs) {
    const { ok, blocked } = rules.availableActions(npc, library, ctx)
    const scored = ok.map(a => scoreOf(a, npc))
    const chosen = pickWeighted(scored)     // 按分数占比抽签
    applyAction(npc, chosen)                // 改状态
    drift(npc)                              // 向基线回归 + 生活压力
    writeCharD1(npc)                        // 数值 → 文本
  }
  
  // 2.3 在场
  const present = presence.resolve(npcs, { roomId: playerRoom, phase, flags })
  
  // ③ 输出
  write('npcs', npcs)
  write('ledger', buildLedger(report))      // 给 AI 看
  write('watch', buildWatch(report, npcs))  // 不给 AI 看
  notifyHooks(report)
}
```
